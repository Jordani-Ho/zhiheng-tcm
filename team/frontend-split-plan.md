## 2. 为什么**不能**一次大拆（有数字的论证）

把 UI 从 `App()` 拆进子组件，有两种走法，**两种都危险**：

### 走法 A：props 透传
`App()` 有 **138 个 state + 118 个内联函数**。要让子组件的交互生效，就得把相关
state 与 setter 以及操作函数逐个传下去。先不说 props 数量，**问题在于**：
这些 state 相互耦合（改 `selectedTeacher` 会牵动 drafts / records / appointments /
calendar / 待办 / 师门上下文…），**props 边界无法静态判定**——只能靠运行才知道漏没漏。

**⇒ 这正是 D-070 那个缺陷的成因**：`clearLineageScopedPanels()` 该被调却漏了一个调用点。
在 138 个 state 的耦合图里，靠人眼维护"哪个操作该触发哪些清理"是不可靠的。

### 走法 B：Context 收口
把 138 个 state 塞进若干 Context。**代价**：Context 值变化会让所有消费者重渲染。
本项目 `App()` 里已有大量"每次渲染新建"的对象/数组字面量，一旦进 Context，
**每次 state 变化都可能引发整树重渲染**——对一个内测产品是性能倒退。

### 走法 C（既有事实）：**先加测试、再拆**
本项目迄今**没有前端测试**，所以任何拆分都**无法自动验证「没拆坏」**。
这是最根本的约束：**拆分的风险 × 验证的缺失 = 不该动**。

## 3. 采用路线：**验证优先的增量抽取**（正在进行）

顺序原则：**先做能"抽成纯函数 + 立刻可测"的部分**，把耦合留在原地不动。

理由：纯函数抽取**风险最低**（无 props 边界、无重渲染、行为可逐条断言），
而且**每条抽取都顺带把一段无人守护的逻辑纳入测试**——是净收益，不是拆东墙补西墙。

### 明确**不做**的

- 不把 `App()` 按"页签"切成 4 个大组件（走法 A/B 的问题未解）
- 不动 JSX 结构（无运行时验证之前，JSX 重组不可验证）
- 不引入状态管理库（内测期增加依赖与学习成本，收益不明）

## 4. 拆分的**准入门槛**（每条抽取都必须满足）

1. 抽出的是**纯函数或自包含组件**（无隐式全局依赖；如需 IO，用依赖注入）
2. 抽取前后**行为逐字等价**（对照 diff 逐条复核）
3. **先写测试再接线**（测试跑绿才改 `App.tsx`）
4. `tsc -b --force` + `npm test` + `vite build` 三项全绿
5. 若发现原逻辑有缺陷 → **单独提交**（如 D-070），不与重构混在一起

---

## 5. 什么时候才动 `App()` 的 JSX

需要**先具备**以下能力之一，否则不做：

- **组件级测试**能覆盖"交互后 DOM 变成什么"（现在只有入口组件有覆盖）
  → 需补 `@testing-library/react` 或等效工具，并把 `App()` 的可测面做大
- 或**端到端测试**（Playwright / vitest browser mode）能跑真实浏览器

**⇒ 结论**：`App()` 的 JSX 大拆**排在补完组件级测试能力之后**。
在那之前，继续走 §3 的纯函数抽取路线。
