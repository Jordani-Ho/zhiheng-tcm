### 3.1 C-1 · 学生引荐链 —— **裁定：先清代码，与白皮书修订解耦** ✅

**裁决理由**：

1. **宪法侧已经明确了**——不是「等白皮书改完才知道该不该做」。v2.1 §2.5.4 已删「引荐亲友」，修订清单第 8 条自述已执行。**方向无歧义**。
2. **§2.8.3 节点 1 的残留不影响「该不该清代码」的判断**——它只影响「白皮书里那处描述怎么办」。**两件事可以分开**。
3. **它是活的越权面**，不是设计债。按设计史 L1078 的定调「不做完，后面的 C2/C3 都在脏地基上」——**我同意这个判断**。
4. **越早清，C 板块的设计越简单**：`REFERRAL_REFERRER_TYPES` 去掉 `STUDENT` 后，引荐链的语义退化为「老师↔老师」，与 §4.1.1「引荐只发生在老师与老师之间」严格一致。

**执行方式（我的技术决定）**：

| 动作 | 内容 |
| :-- | :-- |
| 1 | `REFERRAL_REFERRER_TYPES` → `("TEACHER",)` |
| 2 | `REFERRAL_REFEREE_TYPES` → `("TEACHER",)`（`DEPENDENT` 一并去，依 §4.1.3 监护走子账户，不走引荐链） |
| 3 | 删 `create_student_referral`（service）+ `POST /api/referral/student`（api） |
| 4 | 删 `REFERRAL_ANNUAL_QUOTA` + `count_referrals_by_referrer_in_year`？**→ 否，见下** |
| 5 | 删 4 个学生引荐测试；**新增守护用例**：断言 `/api/referral/student` 返回 404、`STUDENT` 不在类型白名单 |
| 6 | 迁移 `0009`：**清理既有数据库中的学生引荐行**（逻辑隔离，不硬删——见 §3.9 的同一原则） |

**关于 `REFERRAL_ANNUAL_QUOTA`（我与 C 板块的判断不同，说明理由）**：

C 板块清单把它列为「实录要求删」。**我裁定：暂不删，但要改语义**。

- 依据：C 设计 v1 §2.2 已按 §4.1.1 落盘「**老师引荐额度 = 每年 3 位**」（v2.1 未定义额度，属 C 板块自拟约束）。

- **动作**：改名（如 `TEACHER_REFERRAL_ANNUAL_QUOTA`）+ 保留，**不删**。
- **请 C 板块确认**：v1 §2.2 的「每年 3 位」是否确实要保留？若不要，我改判为删除。

**排期**：**列为第一次落地的硬前置**（与 D-019 前端拆分、D-020 身份并列）。**我执行。**

### 3.7 W-13 · 预存 / 扣款 / 负余额 / 信用额度

**裁决：技术上采纳 C 板块的推理；是否入宪归发起人。**

**我复核了代码**：

| 项 | 实测 | 结论 |
| :-- | :-- | :-- |
| `_change_finance_balance` 拦负余额 | `database.py:1394` docstring + `:1398-1400` `if balance + amount < 0: rollback; return {"ok": False, "error": "余额不足"}` | ✅ **确实拦截** |
| 预存制已实现 | `accounts`（`database.py:1336`）+ `transactions` 带 `balance_after`（`:1345`）+ `recharge_account`/`deduct_account`（`:1414`/`:1424`） | ✅ C 板块所述属实 |
| 欠费扫描 | `agent.py:596` `check_billing_alerts` | ✅ 属实 |

**我的技术判断（支持发起人裁定）**：

> 发起人裁定「余额必须可为负」，**技术上必须如此，否则「欠费」这个概念无法表达**。
>
> **C 板块给的推理我认可**：「按次付费」= 先服务后付款 → 服务发生时成本必须记账 → 余额必然暂时为负 → 这正是「欠费」。
> 若拦截负余额，**这笔账记不下来** → `check_billing_alerts` 永远看不到欠费 → **智能体无法生成催缴请示** → 「助理」职责落空。
>
> 且它**自洽于 v2.1 §6.3.6（L1805）**「供养在服务之后发生」。

**但我补两条 C 板块未提的技术要求**：

1. **放开负余额必须与 `credit_limit` 同时落地**——否则「正常按次付费的短暂负数」与「真正赖账」无法区分，催缴会误伤正常用户。
2. **放开负余额是一个安全面变更**：`_change_finance_balance` 是**统一入账入口**（`database.py:1394` 自述），放开它意味着**任何扣款路径都不再受余额约束**。
   → **必须同时加**：① `credit_limit` 上限校验（超限拒绝）；② 欠费事件的审计留痕；③ 单测覆盖「正常负数放行 / 超额度拒绝」两条路径。

### 3.8 W-14 · 归档「可逆」vs「直接删除」

**裁决：采纳 C 板块裁定；其宪法级理由我复核后确认成立。**

C 板块的核心论证是：

> 老师的病历记录里同时含有学生的数据。依 v2.1 §1.2「数据主权归主账户持有者」（L91），硬删会**摧毁学生的主权数据** → 「老师端移除」只能是**可见性移除**，不能是数据销毁。

**我复核 §1.2（L91-95）后确认：这个论证成立，而且它比 C 板块说的还更硬**——v2.1 §5.4.1 数据分类表（L1334起）明确把「病历、处方」归 **主账户持有者**，存储在**客户端**，**是否上链=否**。老师的病历记录**不是老师的数据**，是**学生的数据在老师端的副本**。

**→ 所以「直接删除老师端数据」在宪法上根本不成立**：老师无权销毁学生的数据。

**我的技术裁定**：

| 动作 | 性质 | 可逆 |
| :-- | :-- | :-- |
| **归档（默认）** | **逻辑归档 + 视图隔离** | ✅ 可逆 |
| **数据导出** | 独立可选动作 | — |
| **显式销毁** | ❌ **不做**（老师无权）；若确需，只能是**学生自己**行使数据主权去删 | — |

**须发起人商定**：是否把「归档 = 逻辑归档（可逆）+ 可选导出」写进 v2.1 §4.2.3，并**删除**「直接删除老师端数据」这一选项。
