# 裁决 · 数据主权与「归档 / 封存」的宪法口径

**文件**：`team/decisions/ruling-2026-10-04-数据主权与归档封存.md`
**裁决人**：知衡（CTO）
**日期**：2026-10-04
**溯源**：发起人 2026-10-04 口述宪法规定（经本人逐条核实代码现状）

---

## 0. 发起人原文（不加工，供逐字引用）

> 宪法规定：数据主权归学生主账号，知识产权归老师主账号。
>
> 数据：指学生的完整病历，包括基础信息，症状信息，视频、图像、声音、文字等等。**老师在施治方案签字后，数据就全部转移到学生端，老师端只保留学生基础信息，症状抽象描述（不包含任何原始记录），施治方案。**
>
> 「归档」/「封存」都表示**老师端删除所有学生的信息，包括基础信息，意味着被该老师除名**，但学生端不受影响。
>
> 「封存」指**学生端下线，被社区除名**。

---

## 1. 这条规定的三个要点

| # | 要点 | 含义 |
| :-- | :-- | :-- |
| **1** | **数据转移有时点** | **老师签字后**，学生数据**全部转移到学生端**；老师端只留三样：① 学生基础信息 ② 症状**抽象描述**（不含任何原始记录）③ 施治方案 |
| **2** | **归档 = 封存 = 老师端全删** | 二者都表示「**老师端删除所有学生信息，包括基础信息**」→ 从学生视角 = **被该老师除名**；**学生端不受影响** |
| **3** | **封存 = 学生端下线 + 社区除名** | 这是**学生侧**的动作，与老师侧无关 |

**⇒ 最关键的推论：「归档」与「封存」在老师端是同义动作**，区别只在后续：
- **归档** = 老师单方面移除 → 学生**被该老师**除名（其他师门不受影响）
- **封存** = （学生已被全体老师归档 / 社区除名）→ 学生**端下线** + **社区级除名**

## 2. 🔴 与现状的四处硬冲突（逐条已实测核实）

### 冲突 1 · `DELETE /api/patients/{name}` 是**全局硬删** —— 摧毁学生主权数据

**实测**（`backend/database.py:584-590`）：

```python
def delete_patient(name):
    for table in ["patients", "patient_teachers", "patient_profiles", "homework",
                  "transcriptions", "drafts", "patient_records", "points_accounts"]:
        conn.execute(f"DELETE FROM {table} WHERE {col} = ?", (name,))
```

**前端确实在调它**：`frontend/src/App.tsx:2201` → `fetch('/api/patients/${name}', { method: 'DELETE' })`

**问题**：
- 它**跨全部 8 张表删除**，含 `patient_records`（病历）、`transcriptions`（语音）、`patient_profiles`（基础信息）、`drafts`（病历草案）
- **不区分师门** —— 一位老师「删除」学生，**其他师门的数据也一并消失**
- **删的正是「应该归学生端」的数据** → **老师端在销毁学生的主权数据**

**⇒ 与发起人规定第 1、2 条直接冲突。**

### 冲突 2 · `patient_profiles` **没有 `teacher_name` / `lineage_id`** —— 基础信息无法按师门隔离

**实测**（读 `zhiheng.db` 的 `PRAGMA table_info`）：

| 表 | 有 `teacher_name` / `lineage_id`？ |
| :-- | :-- |
| `patient_records`（病历） | ✅ `['teacher_name', 'lineage_id']` |
| `transcriptions`（语音） | ✅ |
| `drafts`（草案） | ✅ |
| `homework` | ✅ |
| **`patient_profiles`（基础信息）** | ❌ **两个都没有** |

**问题**：
- 上游表的隔离能力**存在**（四张表带 key）
- 但**基础信息表缺 key** → 无法按师门控制「老师端保留学生基础信息」的范围
- 且 `patient_profiles` 存的是 **gender / birth_date / birth_time / birth_place / location** —— 依白皮书 §1.2 分类，**这是「天地呈现」的原材料，本就不属于任何人**；而**姓名与家庭关系**才是主账户的标识

**⇒ 发起人规定第 1 条（老师端只保留基础信息）在当前模型下无法精确实现** —— 因为「基础信息」本身没按师门切分。

### 冲突 3 · 老师端**没有「移除自己名下的学生」这个动作** —— 只有「全删」

**实测**：老师端唯一的删除入口就是冲突 1 的全局 `delete_patient`。

**问题**：发起人规定「归档 = 老师端删所有学生信息」——**动作方向对，但范围错**：
- 应当是：**删老师端自己的那份**（`patient_teachers` 里该老师那一行 + 该老师名下的病历）
- 现状是：**删掉全部**（含学生自己的档案、其他师门的数据）

### 冲突 4 · 白皮书 v2.1 §4.2.2 的表述与发起人规定**方向相反**

**白皮书原文**（L1020–1026）逐字：

> 归档不是除名，不是封存，是老师对自己师门的**轻装**动作。
> 老师端**不再保留**该学生的数据。学生端保留完整数据。

| 维度 | 白皮书 §4.2.2 | 发起人规定 |
| :-- | :-- | :-- |
| 「归档不是除名」 | ❌ 明说不是 | ✅ **就是除名**（「意味着被该老师除名」） |
| 「轻装」 | ✅ 是轻装 | ❌ **不是轻装，是除名** |
| 老师端删什么 | 「该学生的**数据**」 | 「**所有**学生的信息，**包括基础信息**」 |

**⇒ 白皮书 §4.2.2 与发起人口述规定存在实质分歧。**

**而 C 板块的设计正文（`phase3-governance-design-v1.md` §1.3 L112）正是照白皮书写**：

> | **归档** | 师门轻装 | 老师（门规） | 学生 | 老师端移除，**学生端保留** | v2.1 §4.2.2 L1020–1026 |

**⇒ C 板块的 P-304 设计（`archived_at` 逻辑归档 + 视图隔离）依据的是白皮书旧表述，与发起人新规定冲突。**

## 3. 我的处置

### 3.1 立即冻结 P-304，改按新口径重做

| 项 | 原设计（C 板块 P-304） | 新口径 |
| :-- | :-- | :-- |
| 机制 | `patient_teachers` 加 `archived_at` 列，**逻辑归档 + 视图隔离** | **老师端真实删除**该老师名下的学生关联与病历 |
| 可逆性 | 「可逆」（`archived_at = NULL` 即恢复） | **不可逆**（老师端那份已删） |
| 语义 | 「不是除名，是轻装」 | **就是除名**（从该老师） |

**⇒ 好消息**：`archived_at` **尚未实现**（我实测零命中），P-304 **还没开工** → **改动成本为零。**

### 3.2 「封存」必须拆为三个语义

发起人规定「封存 = 学生端下线 + 社区除名」。但白皮书里「封存」还用于**老师智能体**：

| 场景 | 定义 | 出处 |
| :-- | :-- | :-- |
| **A. 老师智能体封存** | 老师被除名，其智能体下线，数据不删 | v2.1 §1.3 L124–128、§1.6 L172 |
| **B. 学生端封存** | **学生端下线 + 社区除名** | **发起人本条新规定** |
| **C. 归档/封存（老师端）** | 老师端删光该学生信息 = 被该老师除名 | **发起人本条新规定** |

**⇒ 术语必须加限定词，否则三义混用无解**：
- A → 「**老师智能体封存**」
- B → 「**学生端封存 / 社区除名**」
- C → 「**师门归档**」（= 老师除名学生）

### 3.3 老师端「保留三样」的技术落点

依发起人规定第 1 条，**签字后**老师端只保留：

| # | 保留物 | 现有承载 | 处置 |
| :-- | :-- | :-- | :-- |
| 1 | 学生**基础信息** | `patients` / `patient_profiles` | ⚠️ 需加师门 key（冲突 2） |
| 2 | 症状**抽象描述**（不含原始记录） | **无独立承载** | 🆕 **需新建**（或明确为 `patient_records` 的脱敏投影） |
| 3 | **施治方案** | `patient_records`? / `prescriptions` | 需明确 |

**⇒ 而「原始记录」（视频/图像/声音/文字全文）必须在签字后从老师端清除 → 当前没有这个机制。**

## 4. 🔴 我必须上报发起人的三处，请裁

### 待裁 1 · 白皮书 §4.2.2 与你的规定冲突，以哪个为准？

| 选项 | 含义 |
| :-- | :-- |
| **A. 以你本次规定为准，改白皮书 §4.2.2** | 需删「归档不是除名，不是封存，是轻装」+ 改「老师端不再保留该学生的**数据**」→「不再保留**该学生的一切信息，含基础信息**」 |
| B. 以白皮书为准，你的规定是补充说明 | 需解释「轻装」与「除名」如何并存 |

**我不擅改白皮书（D-035 第③条）→ 请裁。我的建议：A。**

### 待裁 2 · 「老师端只保留基础信息」——「基础信息」具体指什么？

`patient_profiles` 现有字段：`gender / birth_date / birth_time / birth_place / location`。

依白皮书 §1.2：**姓名 + 家庭关系** = 主账户标识；**性别、出生时间** = 「天地呈现」的原材料。

**⇒ 请确认老师端签字后保留的是哪一份：**

| 选项 | 含义 |
| :-- | :-- |
| **A. 只留姓名 + 家庭关系** | 与 §1.2「老师端不再保留原材料」一致 |
| B. 留姓名 + 出生信息（八字） | 老师需要按八字辨证 |
| C. 全部 `patient_profiles` 字段 | 现状 |

### 待裁 3 · 「归档」与「封存」在老师端同义，那「学生除名三情况」（v2.1 §4.4.2）还成立吗？

白皮书 §4.4.2 定义了三种学生除名：A 老师决定 / B 长期无互动 / C 全体老师除名。

若「归档 = 被该老师除名」，则：
- **情况 A**（老师决定除名）= **一次归档**
- **情况 C**（全体除名）= **被全体老师各自归档**
- **情况 B**（长期无互动）→ 系统提醒老师 → 老师归档

**⇒ 我的理解是：三情况可以被「归档」统一解释，不需要独立的除名动作。请确认。**
