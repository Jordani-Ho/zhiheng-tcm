## 2. 我实测出的另三处硬冲突（须你登记为设计缺口）

### 冲突 1 · `DELETE /api/patients/{name}` 是**全局硬删**，摧毁学生主权数据

**实测** `backend/database.py:584-590`：

```python
def delete_patient(name):
    for table in ["patients", "patient_teachers", "patient_profiles", "homework",
                  "transcriptions", "drafts", "patient_records", "points_accounts"]:
        conn.execute(f"DELETE FROM {table} WHERE {col} = ?", (name,))
```

**前端确实在调它**：`frontend/src/App.tsx:2201` → `fetch('/api/patients/${name}', { method: 'DELETE' })`

**问题**：跨 8 张表全删、**不分师门** —— 一位老师删学生，**其他师门数据也一并消失**；且删的正是「应归学生端」的数据。

### 冲突 2 · `patient_profiles` **缺 `teacher_name` / `lineage_id`**

**实测**（`PRAGMA table_info`）：

| 表 | 隔离 key |
| :-- | :-- |
| `patient_records` / `transcriptions` / `drafts` / `homework` | ✅ 都有 `teacher_name` + `lineage_id` |
| **`patient_profiles`** | ❌ **两个都没有** |

**⇒ 「老师端只保留该学生基础信息」在当前模型下无法按师门控制。**

### 冲突 3 · 老师端**缺「移除自己名下学生」这个动作**

老师端唯一删除入口就是冲突 1 的全局硬删。**缺的是「删老师端自己那份、不动学生端」的动作。**

## 3. 术语处置：三个「封存」必须加限定词

发起人规定「封存 = 学生端下线 + 社区除名」。但白皮书「封存」还用于**老师智能体**：

| 场景 | 建议术语 | 出处 |
| :-- | :-- | :-- |
| 老师被除名，其智能体下线、数据不删 | **老师智能体封存** | v2.1 §1.3 L124–128、§1.6 L172 |
| **学生端下线 + 社区除名** | **学生端封存 / 社区除名** | **发起人本条** |
| 老师端删光该学生信息 = 被该老师除名 | **师门归档** | **发起人本条** |

**⇒ 请在设计正文 §1.3 的术语表中按此三分，并在每个术语后加限定词。**（等发起人裁定「归档是否等于除名」后定稿）

## 4. 🔴 一处你必须登记的新设计缺口（**大缺口**）

**发起人规定第 1 条**：

> 「数据：指学生的完整病历，包括基础信息，症状信息，视频、图像、声音、文字等等。**老师在施治方案签字后，数据就全部转移到学生端，老师端只保留学生基础信息，症状抽象描述（不包含任何原始记录），施治方案。**」

**⇒ 这要求一个当前完全不存在的机制：「签字后数据转移 + 原始记录从老师端清除」。**

| # | 保留物 | 现有承载 | 缺口 |
| :-- | :-- | :-- | :-- |
| 1 | 学生**基础信息** | `patients` / `patient_profiles` | ⚠️ 缺师门 key（冲突 2） |
| 2 | 症状**抽象描述**（不含原始记录） | **无独立承载** | 🆕 **需新建** |
| 3 | **施治方案** | `patient_records`? / `prescriptions` | ⚠️ 归属未明 |

**而「原始记录」在签字后必须从老师端清除 —— 当前无任何机制。**

**登记要求**：在 `phase3-governance-design-v1.md` 的**待填/缺口节**新增一条，标题建议：
**「签字后数据转移机制（数据主权执行点）—— 全新缺口，无设计、无代码」**，内容须含：① 触发点（老师签字）；② 转移什么（原始记录全集）；③ 保留什么（三样）；④ 与 B 板块 B1 加密、B5 导出的关系。

**⚠️ 注意**：这条可能**不属于 C 板块**（更像 B 板块「数据主权」或跨 B/C）。**你只需登记缺口与归属建议，不要自行设计。**
