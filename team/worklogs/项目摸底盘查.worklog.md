## 八、DSH 的观察

1. **`team/` 整个目录未被 git 跟踪，是唯一的 untracked 项。** `team/` 下已有 `README.md` 和 `roles/`、`worklogs/`、`handoffs/`、`decisions/`、`cline-patterns/` 五个空目录。也就是说，团队协作总纲和全部协作产物目前只存在于本地磁盘，没有任何版本保护——而 `team/README.md` 自己写着「文档有状态，对话无状态」「交接必留痕」。这是一处规范与现状的落差，建议发起人决策是否纳入版本库。

2. **后端是「平铺 + 按板块配对」结构，靠文件名而非目录分层。** 39 个顶层 `.py` 中，业务板块呈清晰的 `X_api.py` + `X_service.py` 成对形态：`referral_`、`crypto_`、`learning_`、`lineage_`、`template_`、`agent_stage_` 六对；`witness_` 则独占四个文件（`witness_auth/db/hash/router`），是自带存储与鉴权的独立模块，与 `main.py` 并列。这种结构在 48 个 py 文件的体量下仍可读，但缺少包边界，模块间依赖只能靠 grep 判断。

3. **迁移严格线性，一板块一迁移，且带迁移守卫测试。** `0001`–`0008` 编号连续无缺号、无 merge 分支，命名基本对应板块（`0007` seal、`0008` referral）。同时 `backend/test_migrations.py` 存在，配合 `migrations_runner.py`，说明迁移不只是「写了就算」，有自动化守卫——这是项目里最扎实的一处工程习惯。

4. **前端尚处早期，扁平且无 `.ts` 层。** `frontend/src/` 只有 9 个平铺 `.tsx`，没有 `components/`、`hooks/`、`pages/` 分层，也没有任何纯类型/工具 `.ts` 文件——逻辑全在单文件组件内。同时 `witness.html` + `witness_main.tsx` + `WitnessApp.tsx` 构成一个独立于 `index.html`/`App.tsx` 的第二入口，说明「见证」板块被刻意做成可独立分发的页面。文件数与后端 48 个 py 明显不对称，前端进度落后于后端。

5. **`docs/` 是「设计先行、逐 epic 收口」的节奏证据，且数据库与密钥被正确挡在版本库外。** 22 个文档里，设计文档以 `epic1`–`epic4` 与 `phase2`–`phase4` 分期命名，并存有 `epic3-closure-report-v1.md`（收口报告）、`backlog-white-paper-v2.1.md`、`tech-debt.md`，四版白皮书 `v1.0/v1.1/v2.0/v2.1` 全部留档——`docs/` 跟踪 28 个文件，与 `team/README.md` 所述「设计与执行分离」在目录结构上对得上。另一方面 `.env`、`backend/test.db`、`backend/zhiheng.db`、`backend/zhiheng.db.bak-*`、`backend/backups/`、`backend/uploads/` 均已由 `.gitignore` 排除（已用 `git check-ignore -v` 逐条核实，非推测），数据库与密钥未进版本库。
