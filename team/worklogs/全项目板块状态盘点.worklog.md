## 6. DSH 的观察

1. **四板块的「接口」多数不是 HTTP 契约，而是「同一张 SQLite 表 + 几个预留列」。** 真正决定跨板块耦合的是**谁拥有哪张表**：D 用 `witness_db.py` 的只读 URI 直连同一个库（`file:...?mode=ro`），E 靠 `chain_ready` / `chain_hash` 占位，C 靠 `referral_chain`。所以 E 文档 L79 那份「已建表」清单，其重要性远超一般文档表述——它是 E 板块全部实现工作的对象清单。**清单里有 5 张表不存在，这比任何一个接口路径写错都严重。**

2. **「预留列」策略把交付顺序漂亮地解耦了，但也把风险全部推给了后置的 E。** B / C / D 只建列不填值（`chain_ready` 恒 FALSE、`chain_hash` 恒 NULL），E 的唯一职责被压缩成「填值 + 锚定」。好处是三方可以并行设计；代价是**预留一旦没建，E 的假设就静默落空**——`evidence_hash` 正是这种情况：E 说它「已预留」，C 大纲说 C 要传它，实测它不存在。这类缺口在「设计定稿、实现未启动」的阶段不会报错，只会在 E 启动时集中暴露。

3. **设计与实现的落差是全项目最大的结构性特征。** 四份设计文档全部自称定稿（B v1.3 / C v0.5 / D v1.3.1 / E v0.4），三份施工大纲全部自称「骨架定稿」。而实际代码覆盖：B 约 3/5 子项、C 1/5 子项、D 3/6 模块、E 零。**文档侧的成熟度显著领先代码侧**，且三份大纲的「等待清单」已经部分失效而无人回写（冲突 8 / 10）。

4. **「三份大纲互相等待」的闭环已经部分自动解开，但没人注意到。** C 等 B4 + D 的闭环 → B4 已于 `42b353d` / `246f231` 闭环、C 大纲自己也已把待填项标为「已填」（L111–117）；D 等「C 实现完成」→ C 的引荐链已实现并有 14 项测试、D 自己的 M2/M4 也已实现。**也就是 C 大纲 §3.3 说的「可升 v1.0」在事实上已经成立，但 §5 的下一步表还停在「待 2 + 3」。** 这类「事实已变、文档未变」的漂移，是当前最便宜可修、也最容易继续累积的债。

5. **D 板块的「见证」目前看的是假数据，这一点值得发起人明确知晓。** `WITNESS_USE_MOCK` 默认 `1`，四个只读端点返回硬编码的 `teacher-A/B/C`、`lineage-alpha/beta`；一旦把 mock 关掉，四个端点全部 501 并逐字写「C 板块 XXX 未实现」。配合 D 的鉴权还是 `witness_auth.py` 里两个写死的 token，**D 板块当前是「形状已具备、内容未接通」的状态**——它验证了只读架构（RO 连接、仅 GET、无写路由、12 项测试），但离「真的能看见社区」还有一次真实数据接通的距离。

6. **测试覆盖与板块边界高度对齐，纪律执行得很好。** B=53、D=31、C=14、E=0 个 test 函数，基本一板块一组测试文件，能清楚看出每个板块自证到什么程度。E=0 是合理的（未启动），但要注意 E 文档自己写下的约束「**基线 603 passed 在 E 板块实现期内不减**」（L867）——**目前无人能验证这一条**，因为实际 passed 数需运行 pytest 才能取得（我按边界没跑）。
