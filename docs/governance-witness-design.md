## 1. 目的与范围

### 1.1 为什么需要治理见证入口

白皮书 2.0 §4.1 定义治理原则为「规则前置，不靠事后」。规则前置意味着社区不做事后审判，但当治理动作发生时，社区需要有人能**看见**——不是审判，是见证。

见证的必要性来自白皮书 1.0 §五「去中心化的真实含义」：社区显性化后，如何既被看见、又不被吞没，是根本命题。见证入口是"被看见"的技术答案。

### 1.2 唯一跨师门通道的定位

本入口是社区**唯一**的跨师门通道。

除此之外，一切按 lineage_id 隔离（对齐 Epic 4 §5.3）。老师之间没有直接通道（白皮书 2.0 §4.3.1），学生档案按师门隔离（白皮书 2.0 §2.5.4），治理见证入口是唯一的例外。

例外的正当性来自其**单向只读**属性——通道存在，但不构成通信。见证人看见，但不能介入。

### 1.3 本文不覆盖

- Token / 康币结算（白皮书 2.0 第六章）
- 哈希上链锚定（E 板块）
- 数据加密实现（B 板块 B1）
- 治理动作本身的规则（C 板块）

## 3. 席位机制

### 3.1 构成

9 席 = 2 永久 + 7 推举。

9 席见证人的正式名称为「社区运营管理委员会」（R-009）。「见证人」为正文简称。

### 3.2 永久席位

#### 3.2.1 承担者

| 席位 | 承担者 | 类型 |
| :---- | :---- | :---- |
| 永久-1 | 发起人 | 真人 |
| 永久-2 | 知衡 | 角色 |

#### 3.2.2 不可转移

永久席位**不可转移**。

不可转移的约束写进**合约**，不写进界面。理由：界面约束可被绕过，合约约束不可。这与白皮书 2.0 §七「代码即法律」一致。

#### 3.2.3 休眠

两席永久席位的休眠条件**不同**，不共用一套规则。

##### 永久-1（发起人）

| 项 | 内容 |
| :---- | :---- |
| 休眠条件 | 承担者离世或被淘汰 |
| 可逆性 | **不可逆** |
| 理由 | 永久席位的正当性来自承担者本人，不来自席位本身 |

##### 永久-2（知衡角色）

| 项 | 内容 |
| :---- | :---- |
| 休眠条件 | **仅**「角色无承担者超过 N 天」 |
| 可逆性 | **可承接** |
| 不触发休眠 | AI 迭代、模型升级、知衡角色版本演进 |
| 理由 | 知衡是**角色**，不是真人；角色可承接，AI 迭代 ≠ 角色无承担者 |

##### 休眠的通用语义

- 席位**保留**，不空缺，不继承，不转移。
- 入口对该席位返回**只读历史**——既往见证记录仍可查。
- 休眠席位**不再参与**无异议窗口（§3.3.3）。
- 休眠席位**不计入**活跃席位数。

**N 的取值**：归开放问题（§10.6）。

### 3.3 推举席位

#### 3.3.1 原则

| 原则 | 说明 |
| :---- | :---- |
| 宁缺毋滥 | 允许席位空缺，不凑数 |
| 无任期 | 不设换届，不设连任限制 |
| 综合指标作参考 | 学生数 / 活跃数 / 好评率，**不写硬门槛** |
| 无异议即生效 | 见 §3.3.3（已回流为 R-011） |

综合指标**仅作提名参考**，不写硬门槛。理由：写死门槛会催生刷指标，与白皮书 2.0 §4.2.3「门限不是考核，是自然筛选」相悖。

**标注**：表中「宁缺毋滥」「无任期」为 **D 板块自拟**，不在 R-009 内。R-009 只定义"允许空缺"。若需进 R-009，由发起人裁决。

#### 3.3.2 提名环节

提名通过**老师智能体 + agent_tasks 请示链路**完成（复用白皮书 2.0 §2.8.3 节点 3）。

| 步骤 | 谁做 | 做什么 |
| :---- | :---- | :---- |
| 1 | 系统 | 定期扫描综合指标，产生候选池 |
| 2 | 系统 | 按确定性规则选一位现任见证人为「提议者」 |
| 3 | 提议者的老师智能体 | 收候选 → 向老师发起**请示** |
| 4 | 提议者（老师） | **批准 / 忽略**——二元决定 |
| 5 | 批准 → 提名上链；忽略 → 本轮作废 | |

老师这边只看到一条请示，点一下。**找谁、比什么、写什么，全是智能体干的**。

理由：老师闲云野鹤，不争名利，不该被治理事务打扰（白皮书 2.0 §2.3.3「不做诊断之外的杂务」）。行政包袱归老师智能体。

**扫描触发的归属**：定期扫描由**协议层定时任务**触发，**不属于平台**。

理由：平台不介入治理（白皮书 2.0 §6.5.6「志愿团队只维护基础设施，不介入师生关系」）。扫描是协议行为，不是平台行为。

提议者轮转规则为开放问题（§10.1）。

#### 3.3.3 确认环节（无异议窗口）

| 步骤 | 谁做 | 做什么 |
| :---- | :---- | :---- |
| 1 | 其余 8 席的老师智能体 | 收到「待确认」请示 |
| 2 | 8 位老师 | 不响应 = 无异议；明确忽略 = 异议 |
| 3 | N 天到期无异议 → 生效上链 | |
| 4 | 有异议 → 退回提名方 | |

**N = 14 天，配置项，可调。**

**标注**：「N = 14 天」为 **D 板块自拟**，不在 R-009 内。R-009 只定义"24 小时内公开"（针对证据模式开启，见 §5.5.2），未定义无异议窗口时长。若需进 R-009，由发起人裁决。

**关键**：老师的"沉默"是**无异议**，不是**弃权**。

理由：老师本来就不关心谁当见证人，沉默就是默认。这与白皮书 2.0 §4.6.2「一位老师愿意接纳就够了」同构——**主动行为才是否定**。

本环节不是「投票」。差别在于：

- 投票是主动行为，会把见证人变成议员。
- 无异议是被动行为，见证人仍是观察员。

**标注**：「无异议即生效」机制**已回流为 R-011**（见附录 A）。R-009 定义了 7 推举席位但未定义产生机制，R-011 补此结构性缺口。

##### 席位过少保护

**活跃席位 < 5 时**，暂停无异议机制。

本处「活跃席位」= **推举席位中的活跃席位**（与 R-009 对齐）。永久席位不计入本节"活跃席位"的计数——永久席位不可转移，其休眠是独立语境（见 §3.2.3），不参与本节"是否过少"的判定。

此时席位产生 / 罢免需**全部活跃席位明确同意**（不再是无异议即生效）。

**理由**：无异议机制的前提是"沉默者众，默认即同意"。活跃席位过少时，沉默者不足，无异议会退化为"少数人决定"。此时改为主动同意，宁可慢，不可偏。

**标注**：本节「暂停无异议机制 + 改为全部活跃席位明确同意」为 **D 板块自拟**，不在 R-009 内。R-009 原文只定义"推举席位 ≥5 席活跃才合法运转"，未定义"不合法运转"时的具体处置。若需进 R-009，由发起人裁决。

#### 3.3.4 罢免环节

同一路径，反向。

任意现任见证人的老师智能体可发起「罢免请示」→ 老师批准 → N 天无异议窗口 → 生效。

#### 3.3.5 空缺

允许席位空缺。空缺席位：

- 不计入活跃席位数。
- 不参与无异议窗口。
- 不阻塞其他席位运行。

### 3.4 观察员边界

见证人是**观察员**，不是议员。

#### 3.4.1 不做什么

| 不 | 依据 |
| :---- | :---- |
| 不表决 | 白皮书 2.0 §4.1「规则前置，不靠事后」——见证人不做事后审判 |
| 不否决 | 白皮书 2.0 §4.3「天然围墙」——见证人不引入新的治理中心 |
| 不审判 | 白皮书 2.0 §4.6「无审判庭」——见证人不投票 |

引入表决 = 引入政治，与去中心化冲突。

#### 3.4.2 做什么

| 做 | 说明 |
| :---- | :---- |
| 只读观察 | 读取 C 板块治理事件 |
| 快照验证 | 校验哈希快照 |
| 异常标记 | 标记异常，**标记 ≠ 处置** |

见证人的武器是**记录 + 哈希快照**，不是投票。

### 3.5 本章小结

- 9 席 = 2 永久 + 7 推举。正式名称「社区运营管理委员会」。
- 永久席位不可转移，写进合约；永久-1 承担者离世/淘汰 → 不可逆休眠；永久-2 角色无承担者超过 N 天 → 可承接休眠。
- 推举席位宁缺毋滥，无任期，无异议即生效（R-011），N=14 天。
- 见证人 = 观察员，不表决、不否决、不审判。

## 4. 只读总览入口

### 4.1 唯一跨师门通道

本入口是社区唯一的跨师门通道（§1.2）。其正当性来自单向只读属性——通道存在，但不构成通信。

### 4.2 RO 连接

#### 4.2.1 独立模块

RO 连接使用**独立模块**，**不复用** `database.py` 的任何代码。

理由：复用读写连接会引入写路径，只读约束形同虚设。

推荐模块名：`witness_db.py`（或 `database_ro.py`）。

#### 4.2.2 技术约束

| 约束 | 实现 |
| :---- | :---- |
| 独立连接 | 独立于 `database.py` |
| 只读 | SQLite `file:...?mode=ro` URI + `uri=True` |
| 独立账号 | 独立于读写账号（如适用） |
| 独立连接池 | 不与读写连接池共享 |
| 独立超时 | 不与读写超时共享 |

#### 4.2.3 最小权限原则

RO 连接**只读**，不写、不建、不删、不迁移。

### 4.3 API 层

#### 4.3.1 独立 router

| 项 | 值 |
| :---- | :---- |
| 前缀 | `/api/v1/witness/` |
| 方法 | **仅 GET** |
| 强制方式 | OpenAPI 层强制，**非约定** |
| 禁止 | 任何 POST / PUT / PATCH / DELETE 路由**不注册** |

#### 4.3.2 鉴权

见证人身份（公钥）。信任根分层见 §8.2。

#### 4.3.3 不注册写路由

写路由**不注册**，不是"注册后返回 403"。

理由：不注册 = 攻击面为零。返回 403 = 路由存在，可被探测。

### 4.4 前端

- 单向只读页。
- 无表单、无按钮提交。
- 与老师端 / 学生端 UI **完全隔离**——不共享组件的写操作部分。

### 4.5 观察对象

| 观察对象 | 来源 |
| :---- | :---- |
| C 板块治理事件（除名 / 引荐 / 底线触发） | C 板块 §11.3 只读接口 |
| 师门元数据（lineage_id、师生数、活跃度） | C 板块 §11.3 |
| 哈希快照与验证结果 | 本板块 §6 |
| 状态判断（state_judgment） | C 板块 v0.5 §6.6（消费，不定义） |

### 4.6 不展示

| 不展示 | 理由 |
| :---- | :---- |
| 原始病历 | 数据主权归患者（白皮书 2.0 §1.2） |
| 舌苔照 | 同上 |
| 语音 | 同上 |
| 处方明文 | 知识产权归老师（白皮书 2.0 §1.2） |

链上无隐私，链下有数据。见证人看见的是**治理动作的元数据**，不是**诊疗内容**。

## 5. 证据模式双轨

### 5.1 路线 1：事后知情

#### 5.1.1 场景

**R-009 场景标签**：严重违规。

治理事件已发生 → 见证人回溯哈希快照。

#### 5.1.2 患者数据的知情边界

事后知情涉及患者数据时，需与 B 板块 B1（数据加密）对齐知情边界（§5.4）。

### 5.2 路线 2：事前同意

#### 5.2.1 场景

**R-009 场景标签**：纠纷调停。

涉及患者数据进入证据链 → 事前取得同意。

#### 5.2.2 同意粒度

| 粒度 | 说明 |
| :---- | :---- |
| 师门级 | 加入师门时一次性同意 |
| 事件级 | 每次涉及数据时单独同意 |
| 时间级 | 一段时间内有效 |

**CTO 倾向**：师门级默认 + 事件级升级。即加入师门时默认师门级同意；涉及具体患者数据进入证据链时，升级为事件级单独同意。

**状态**：挂起，归 B1 × D 交叉契约，等 B1 定稿（§10.2）。

#### 5.2.3 撤销机制

学生可随时撤销同意。撤销后：

- 后续证据链不再包含该学生数据。
- 既往已上链快照不可撤销（哈希不可逆）。

### 5.3 双轨切换与并存

路线判定有**两个并行判据**：

| 判据 | 来源 | 说明 |
| :---- | :---- | :---- |
| 数据轴 | D 板块 v1.2 原设计 | 是否涉及患者数据 |
| 场景轴 | R-009 原文 | 纠纷调停 / 严重违规 |

两轴**并行**，不互斥，不替换。

- 路线 1 是默认。
- 路线 2 在涉及患者数据时**必须**触发（数据轴）。
- R-009 场景标签（纠纷调停 → 路线 2；严重违规 → 路线 1）作为**并行判据**，用于快速归类。
- 两轨并存，不互斥。

**两轴冲突时的优先级**：待定，归开放问题（§10.8）。当前默认数据轴优先——因为数据主权是宪法级约束（白皮书 2.0 §1.2）。

**标注**：本节「数据轴」为 **D 板块 v1.2 原设计**；「场景轴」引自 R-009。两者并行，D 板块不替换 R-009 场景标签。

### 5.4 与 B1 数据加密的对齐点

本节是 **D ↔ B 的接口契约**。

| 项 | 内容 |
| :---- | :---- |
| 加密后哪些字段可进快照 | 待 B1 定义（§10.3） |
| 哪些字段永不进快照 | 原始病历 / 舌苔照 / 语音 / 处方明文 |

对齐原则：**链上无隐私，链下有数据**。

### 5.5 证据模式开启程序

证据模式（路线 1 / 路线 2）**不默认开启**。开启需满足以下程序。

#### 5.5.1 开启主体

以下任一主体可发起开启：

| 主体 | 条件 |
| :---- | :---- |
| 永久席位 | **单独**即可发起 |
| 推举席位 | **≥ 3 席联署**方可发起 |

永久席位单独开启的正当性来自其不可转移属性（§3.2.2）——永久席位的承担者是社区的锚，锚可单独动作。

推举席位需 ≥ 3 席联署的正当性来自其可产生性（§3.3）——推举席位由无异议流程产生，单独动作不足以代表其正当性。

#### 5.5.2 公开时限

开启发起后 **24 小时内**，向**全体见证人**公开。

公开内容（对齐 §4.6「不展示」）：

| 公开 | 不公开 |
| :---- | :---- |
| 开启发起人 / 联署席位 | 原始病历 |
| 开启理由（一句话） | 舌苔照 |
| 开启范围（师门 / 事件 / 时间） | 语音 |
| 开启对应的事件哈希 | 处方明文 |

公开 ≠ 数据可见。公开的是**开启动作的元数据**，不是**被开启的数据本身**。

#### 5.5.3 开启的哈希快照

开启动作为治理事件，生成哈希快照（§6）。

`event_type = EVIDENCE_MODE_OPEN`

快照字段与 §6.2 一致。

#### 5.5.4 开启 ≠ 走哪条轨

开启只是**让数据进入见证链**。

走路线 1（事后知情）还是路线 2（事前同意），由 §5.3 双轨切换与并存规则决定，与开启程序独立。

#### 5.5.5 与观察员边界的关系

开启是**观察员的内务**，不是治理动作。

- 开启不触发任何处置。
- 开启不改变任何师门状态。
- 开启不豁免见证人的除名（§8.4）。

依据白皮书 2.0 §4.3「天然围墙」——开启只在见证层发生，不越界到治理层。

## 6. 哈希快照

### 6.1 哈希口径

**直接引用** `docs/epic3-learning-design-v1.md` §2.3。

口径已在 3.2 冻结，包含：

- `canonical_json`
- `GENESIS_HASH`
- `PAYLOAD_HASH_ALGO`
- `CANONICAL_SORT_KEYS`

**不需要等 A 板块 3.5。** 哈希口径已锁，D 板块直接引用。

**复用范围**：

- 复用 Epic 3 §2.3 的 `canonical_json` + `sha256_hex` **函数**。
- **不复用** Epic 3 的 9 键结构（那是 `agent_learning_events` 专属）。
- D 快照使用独立的 **8 键**哈希集（见 §6.2）。
- **import 声明**：D 代码只 import `GENESIS_HASH` / `canonical_json` / `sha256_hex` 三项。`PAYLOAD_HASH_ALGO` / `CANONICAL_SORT_KEYS` 是 Epic 3 §2.3 的常量，其语义已被上述函数内部实现吸收，D 代码**不显式 import**。

### 6.2 快照内容与结构

JSON schema（草案）：

```json
{
  "snapshot_id": "...",
  "event_type": "...",
  "event_source": "C 板块",
  "lineage_id": "...",
  "event_payload_hash": "...",
  "canonical_sort_keys": true,
  "genesis_hash": "...",
  "timestamp": "...",
  "witness_seats": [...],
  "snapshot_hash": "..."
}
```

**哈希范围**：

- **参与**快照哈希的字段 = `D_SNAPSHOT_HASH_KEYS`（8 键，见 `backend/witness_hash.py`）：
  `snapshot_id` / `event_type` / `event_source` / `lineage_id` / `event_payload_hash` / `canonical_sort_keys` / `genesis_hash` / `timestamp`。
- **不参与**快照哈希的字段：
  - `witness_seats` —— 随席位变更 / 休眠变化，纳入会破坏确定性。
  - `snapshot_hash` —— 快照自含哈希，纳入自身哈希构成自指。

**字段语义**：

- `canonical_sort_keys` = **布尔** `true`，与 Epic 3 §2.3 的 `CANONICAL_SORT_KEYS` 同源。语义为"哈希时按 sort_keys 排序"，**非键集列表**。
- `snapshot_hash` 由写入方（M2 / M3）在计算快照哈希后追加。本字段**不参与**自身哈希。
- 快照 hash schema 未来版本锚定使用 `hash_schema_version` 字段（**待启用**），不挤进 `canonical_sort_keys`。

### 6.3 生成时机

| 时机 | 触发 |
| :---- | :---- |
| 事件触发 | C 板块治理事件发生 |
| 周期 | 定期快照（周期待定） |
| 手动 | 见证人手动触发（待定） |

### 6.4 存储

- 本地存储。
- 未来上链锚定（E 板块预留）。

### 6.5 诚实边界

快照**能**证明：

- 某事件在某时刻存在。
- 事件内容未被篡改。

快照**不能**证明：

- 事件内容本身是否真实。
- 患者数据是否合规采集（归 B 板块）。
- 治理动作是否正当（归 C 板块）。
