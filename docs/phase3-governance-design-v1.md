### 2.1 M1 的覆盖范围与三扇门归属

白皮书 v2.1 §4.1（L980–1005）定义**三扇门**，都是单向的：

| 门 | 原文（v2.1） | 行号 | M1 覆盖 |
| :-- | :-- | :-- | :-- |
| **引荐** | 老师引荐老师。为对方医德医术背书。火种。 | L984 | ✅ **M1 主体** |
| **邀请** | 老师邀请学生。老师发邀请码（具体手段可替换）。收徒。 | L985 | ❌ **不覆盖**（见 T-3） |
| **监护** | 学生为法律上不具有独立意志/人格的人开子账户。代管。 | L986 | ❌ **不覆盖**（见 T-3） |

**约束**（v2.1 §1.1 第一条铁律 L63–68）：

- 不宣传、不推广、不拉新。社区不投放广告，不做裂变，不搞「邀请好友得奖励」。
- 每个老师都是被其他老师**亲手引荐**的。
- **引荐是老师进入社区的唯一天然路径**——v2.1 §6.2.2 L1702–1708：从徒弟到老师「不经过社区的『出师流程』，只经过一件事：另一位老师愿意引荐他……没有第二条路，也没有额外的出师步骤」。→ **引荐链是师承关系的唯一技术载体**。

> ⬜ **T-3 待确认**：「邀请」与「监护」两扇门无模块归属。v0.5 §3 只覆盖了「老师引荐老师」+「学生引荐亲友」，未覆盖**老师邀请学生**的码 / 审核 / 审批链路。发起人判断 4 只裁定了口径（M1/M2/M3），未裁定三扇门映射。**本文档不自行分配。**

### 2.2 老师引荐老师

**依据**：v2.1 §4.1.1（L988–992）

**语义**（v2.1 L990，逐字）：

> 引荐不是「审核资格」，是「我愿意为他背书」。

**上链要素**（v2.1 L991，逐字）：

> 引荐记录上链：**引荐人、被引荐人、引荐时间、引荐理由（一句话）**。

**理由要求**（v2.1 L992）：「引荐理由不需要长，一句话就够。比如：『此人跟我学过三年，我看过他看病。』」

**流程**：

```
现任老师 → 发起引荐 → 填写 referee_id + referral_reason
  → 写 referral_chain（referrer_type=TEACHER）
  → 被引荐老师建立自己的 lineage_id
```

**约束**（v0.5 §3.2 L178–182 沿用 + 依据重核）：

| # | 约束 | 依据 |
| :-- | :-- | :-- |
| 1 | `referral_reason` **必填**，一句话 | v2.1 L991–992 |
| 2 | **不得自引荐**（`referrer_id != referee_id`） | 逻辑必然；v2.1 未明写 → `⬜ 本文档自拟约束` |
| 3 | 被引荐老师若已有 `lineage_id`，**保留源流**，新师门独立编号 | v0.5 §3.2 L182；v2.1 §1.6 L169「源流可追」 |
| 4 | 引荐**单向、一次性** | v2.1 §4.3.1 L1053 |

> ❌ **已修正**：v0.5 §3.2 L174 引用「老师准入（白皮书 **§4.2.1**）」在 v2.1 下**已失效**——v2.1 §4.2.1 是「为什么要有门规」，与老师准入无关。v2.1 修订清单 L2064 自己做了这次改号：「§4.2.1 老师准入 → **§4.1.1 引荐**」。本文档已按 §4.1.1 重引。

### 2.3 学生引荐亲友

**依据**：v2.1 §2.8.3 节点 1（L679–681）

```
学生 → 引荐 → 亲友 → 老师智能体审核 → 老师最终审批 → 加入。
```

**流程**（v0.5 §3.3 L188–193 沿用）：

```
学生 → 发起引荐 → 选择亲友类型
  ├─ 可自理者 → 老师智能体审核 → 老师审批 → 学生准入
  └─ 不能自理者/未成年人 → 直接作为被照护者（监护模式）
  → 写 referral_chain（referrer_type=STUDENT）
```

**额度限制**（v0.5 §3.3 L195–199）：

| 项 | 值 | 依据 |
| :-- | :-- | :-- |
| 每位学生每年最多引荐 | **3 位亲友** | ❌ **v0.5 自拟，v2.1 未定义** |
| 额度重置 | 按自然年 | ❌ **v0.5 自拟** |
| 被照护者是否占额度 | 占用，与独立学生同等计数 | ❌ **v0.5 自拟** |

**约束**：

- 引荐人必须信誉良好（无未了结的协议底线封存）。
- 被引荐人若曾被所有老师除名，不可再入（v2.1 §4.4.2 情况 C L1100–1101；亦见 §6.2 T-6）。

> ❌ **T-5 待确认（高风险，v2.1 内部矛盾）**：v2.1 §2.5.4「学生的权力」（L515–521）**已删去「引荐亲友」**，改为「为法律上不具有独立意志/人格的人开子账户」（修订清单 L2057 逐字：「§2.5.4 学生权力：去『引荐亲友』，改为『开子账户』」）。

### 2.4 引荐人信誉降级

**依据**：v0.5 §3.4（L206–217）+ **`docs/phase4-decentralization-design.md` §3.2.3（L306–343）**

**原则**：**不连坐，只降级。**

| 事件 | 引荐人影响 | 依据 |
| :-- | :-- | :-- |
| 被引荐人被**一位**老师除名 | 无影响 | v0.5 §3.4 L212 |

| 引荐人主动撤回背书 | 无影响（**撤回是权利**） | v0.5 §3.4 L215 |

**上链口径已由阶段四定义**（`phase4-decentralization-design.md` §3.2.3 L310–322）——**本文档采纳，不重定义**：

| 列 | 类型 | 说明 |
| :-- | :-- | :-- |
| `reputation_event_id` | TEXT PK | 事件 ID |
| `subject_id` | TEXT | 受影响主体（引荐人 / 老师） |
| `event_type` | TEXT | `REFERRAL_DEREGRADE` \| `BOTTOMLINE_DEREGRADE` |
| `delta` | INTEGER | 降级级数（C §3.4：降 1 级） |

| `chain_ready` / `chain_hash` | — | 回填列 |

**硬约束**（阶段四 §3.2.3 P1 L324–329，本文档采纳）：

### 3.1 天然围墙 ✅ **T-1 已裁决**

**依据**：v2.1 §4.3.1（L1045–1056）+ §5.5.4（L1493–1501）

**社区结构决定恶行不可发散：**

- 老师之间**没有直接通道**：没有群组，没有私信，没有联盟，**没有投票**。（L1049）
- 老师只能通过**两种方式**与其他老师发生关系：
  1. **引荐**：老师引荐老师，**单向，一次性**。（L1053）
  2. **学生**：学生同时跟随多位老师，但**老师之间不因此产生直接联系**。（L1054）
- 一个老师招摇撞骗，只影响他自己的师门。他**不能串联其他老师，不能形成帮派，不能集体行骗**。他的恶行**止于他的师门边界**。（L1056）

**技术实现**（v2.1 §5.5.4 L1493–1501，**v0.5 漏抄，本文档补入**）：

| 技术约束 | 原文 |
| :-- | :-- |
| 老师端之间**没有 P2P 连接** | L1496 |
| 老师之间**没有群组、私信、联盟** | L1497 |
| 老师只能通过**引荐链**发生关系 | L1498 |
| 老师只能通过**学生间接**发生关系 | L1499 |
| **恶行不可发散，是技术架构的天然属性** | L1501 |

> ✅ **T-1 裁决：论证成立，采纳。**
>
> **冲突点**：v2.1 §4.3.1 L1049 明写老师之间「**没有投票**」，而发起人判断 1 引入「治理见证人 3 席联署」。
>
> **裁决**（发起人）：v2.1「没有投票」的**主语是「老师之间」，不含见证人**。**联署 ≠ 投票。**
>
> **本文档落为约束**：
> 1. 「没有投票」的作用域**严格限定为老师之间**（v2.1 L1049 的上下文是 §4.3.1 天然围墙，主语为老师）。
> 2. **见证人联署不是老师之间的投票**——见证人是 D 板块的**观察员**，不是议员。援引 `docs/governance-witness-design.md`：
>    - L221「见证人**是观察员，不是议员**」
>    - L227–229「**不表决**（白皮书 §4.1 规则前置）/ **不否决**（§4.3 天然围墙）/ **不审判**（§4.6 无审判庭）」
>    - L241「见证人的武器是**记录 + 哈希快照**，不是投票」
> 3. **技术约束**：3 席联署的产物是 **D 板块的席位事件记录 + 哈希**（§3.4 步骤 4），**不是表决结果**。C 板块**不实现任何投票数据结构、不实现票数统计**。
> 4. **红线**：**老师不得介入联署**。老师对封存决议不投票、不表态、不参与——否则直接违反 L1049。

**依据**：v2.1 §4.5.2（L1121–1132）+ §4.5.3（L1134–1139）——语义已完全确定，直接落为流程：

```
被封存者 → 线下找到一位现任老师
  → 老师愿意接纳
  → 恢复原有封存的数据权限
  → 重新上线
```

**逐字要点**：

- 社区**不设申诉庭，不做审判**。（L1123）
- **一位老师愿意接纳，就够了。**（L1131）
- 「不需要审判，**不需要投票，不需要社区共识**。」（L1130）
- 这位老师，**为重新入社区者背书**。（L1132）
- 封存何时解除？**当一位现任老师愿意接纳他时。**（L1138）
- 没有老师愿意接纳，封存就持续——**这是事实的自然结果，不是社区的判决**。（L1139）

**技术实现**：`unseal_agent(agent_id, sponsor_teacher_id, timestamp)` — **签名以 B4 为准**（§7.2）。

> ✅ **T-7 已判定（本稿判定，请确认）**：**解封不需要 3 席联署**。
> 依据：v2.1 L1130 明写「不需要审判，**不需要投票，不需要社区共识**」；L1131「一位老师愿意接纳，就够了」。
> → 解封路径的共识门槛为 **1 位现任老师**，与封存的 3 席门槛**不对称**。这是白皮书的明文设计，不是遗漏。
> ⚠️ **须补**：由于解封不经 D 板块联署，**D 的席位事件表不会记录解封** → D 侧观察到的将是「已封存」而不是「已解封」。**须确认 D 侧如何获知解封**（T-7b）。

## 5. X1 康币

**来源**：白皮书 v2.1 §6.3（L1724–1841，全八小节）+ §5.5.2（L1444–1483）+ §6 章首（L1664–1691）
**继承**：`docs/phase3-governance-design.md` §7（L580–663）沿用结构，**依据重核**
**实现状态**：⏳ 未实现（无表、无端点、无 flag）——据 `全项目板块状态盘点.worklog.md` L48

> ⬜ **T-8 待确认**：发起人判断 4 只裁定了「统一用 M1/M2/M3」，未提及康币归属。本稿按判断 5 的骨架结构（「康币（继承 v0.5 §7）」）**独立成章为 X1**。若康币应算作「第四模块」，则与 `team/README.md`「三个模块」口径冲突，须发起人明确。

### 5.1 定位重申

**依据**：v2.1 §6.3.1（L1724–1741）+ §5.5.2.2（L1474–1477）

逐字要点：

- **Token 不叫「钱」，叫康币。**（L1726）
- 康币是**社区币**。类比虚拟「饭菜票」，但**只在社区内部有意义**。（L1728）
- **不是货币，不流通，不炒作。** 它是**成本分摊的单位**，是**社区外交易的镜像映射**。（L1730）
- **社区与现实世界没有支付兑换接口，也不打算有接口。**（L1737）
- **钱在社区外走，账在社区内记。康币只是账。**（L1739）
- **医不扣门，道不轻传。康币不是「学费」，是供养。**（L1741）

**§5.5.2.2 技术定位**（L1475–1477，与运营侧一致）：Token 不是货币、不流通、不炒作；是成本分摊的单位；是社区外交易的镜像映射。

**§5.5.2.3 本阶段的正确姿势**（L1478–1483，**对 C 板块直接约束**）：

> 因为社区的当务之急，是先把师承跑通，把智能体跑通，把数据主权跑通。
> Token 的详细设计，涉及经济模型、法律合规、跨区域结算，牵一发动全身。现在不展开，只在白皮书里保留入口。
> **入口保留，方向明确，细节后定。**

→ **技术结论**：C 板块本阶段只做**表结构 + 记账语义 + 入口预留**，**不做经济模型**。这与 §1.4「不接支付通道」一致。

### 5.2 成本结构

**依据**：v2.1 §6.3.2（L1742–1760）**原文表**

| 成本类型 | 承担方 | 换算方式 |
| :-- | :-- | :-- |
| 老师时间 | **学生** | 按诊疗时长、复杂程度换算 |
| 智能体算力 | **学生** | 按 API 调用量、模型规模换算 |
| 电力 | **平台 + 老师** | 按服务器能耗分摊 |
| 存储 | **学生** | 按数据量、存储时长换算 |
| 网络交换 | **平台 + 老师** | 按带宽占用分摊 |

✅ **已核**：v0.5 §7.2（L591–599）与 v2.1 §6.3.2 **逐条逐字一致**（五类、承担方、换算方式全同）。本表直接可用。

**平台位置**（v2.1 §6.3.2 注，L1763，**v0.5 漏抄**）：

> 平台不拥有数据，不拥有知识。平台只提供协议、身份、路由、存储、结算。**平台通过提供基础设施，获得一部分康币分成。**

**§6.3.1 成本项列举**（L1732–1735，与上表互为印证）：老师的时间 / 智能体的算力 / 电力、存储、网络交换 —— 换算成康币，**各方按规则分摊和承担**。

### 5.3 记账模型

**依据**：v2.1 §6.3.6（L1800–1813）+ §6.3.1（L1739）+ §5.5.2.1（L1460–1473）

**核心链路**（v2.1 §6.3.6 L1800–1813，逐字）：

> 学生和老师的供养，**在社区外完成**。
> 学生在社区外，以**法币或其他方式**，向老师表达供养。
> 老师收到供养，**在社区内确认**。
> 确认数据映射进社区相应位置，**生成康币记录**。

**数据模型**（v0.5 §7.3 L605–629 沿用）：

```
community_external_tx (
  tx_id            TEXT PRIMARY KEY,
  from_party       TEXT NOT NULL,      -- 学生（社区外）
  to_party         TEXT NOT NULL,      -- 老师（社区外）
  tx_type          TEXT NOT NULL,      -- OFFERING | INFRASTRUCTURE
  tx_amount_fiat   DECIMAL,            -- 社区外法币金额（仅记录，不结算）
  tx_currency      TEXT,               -- 法币币种
  occurred_at      TIMESTAMP NOT NULL,
  confirmed_by     TEXT NOT NULL,      -- 社区内确认人
  confirmed_at     TIMESTAMP NOT NULL
)

kangbi_ledger (
  ledger_id        TEXT PRIMARY KEY,
  tx_id            TEXT NOT NULL,      -- 关联 community_external_tx
  account_id       TEXT NOT NULL,      -- 老师/平台/公共池
  account_type     TEXT NOT NULL,      -- TEACHER | PLATFORM | PUBLIC_POOL
  amount_kangbi    DECIMAL NOT NULL,
  direction        TEXT NOT NULL,      -- IN | OUT
  created_at       TIMESTAMP NOT NULL,
  chain_ready      BOOLEAN DEFAULT FALSE,
  chain_hash       TEXT
)
```

**字段依据核对**：

| 字段 | v2.1 依据 | 状态 |
| :-- | :-- | :-- |
| `tx_amount_fiat` / `tx_currency` | L1805「以**法币**或其他方式」+ L1824「法币有国界」 | ✅ 可依 |
| `from_party` / `to_party` | L1805–1806（学生 → 老师） | ✅ 可依 |
| `confirmed_by` / `confirmed_at` | L1806「老师收到供养，**在社区内确认**」 | ✅ 可依 |
| `tx_type`（`OFFERING\|INFRASTRUCTURE`） | L1732–1734（供养 vs 成本项）+ L1763（平台基础设施） | ⬜ 枚举为 v0.5 自拟，v2.1 未给枚举 |
| `account_type`（`TEACHER\|PLATFORM\|PUBLIC_POOL`） | §6.3.3 L1767–1778（老师 / 平台 / 公共池三流向） | ✅ 可依 |
| `amount_kangbi` / `direction` | L1732–1735 换算 + L1782 结算 | ✅ 可依 |
| `chain_ready` / `chain_hash` | §6.3.4 L1783「**结算上链，不可篡改**」+ §5.1.3 L1199 | ✅ 已核 |

**原则**（v2.1 §6.3.5 流通边界 L1787–1793，逐字）：

- 康币**只能在社区内流通**。
- 康币**不能兑换法币**。
- 康币**不能转让给第三方**。
- 康币**不能用于社区之外的任何场景**。
- 康币**只能用于社区内部的成本分摊与供养**。

**理由**（v2.1 L1799，逐字）：因为康币不是货币。它是社区内部的记账单位。一旦开通对外接口，就会脱离社区，就会变成货币，就会吸引投机，就会偏离「供养」的初衷。

> ⚠️ **技术约束（必须写进实现红线）**：`kangbi_ledger` **不得有任何对外兑换 / 转让 / 提现路径**。这不是「本阶段不做」，是**永久约束**（v2.1 L1737「也不打算有接口」）。

**「确认」的性质**（v2.1 全文交叉引用）：

- 康币确认是「老师确认」上位抽象的一个原语（v0.5 附录 C §2.3.6 L923–930，来源 B 板块 v1.1 需求，C v0.5 采纳）。→ **本阶段沿用**，不新增数据结构、不新增 API。

### 5.5 社区外交易的镜像映射与跨境

**依据**：v2.1 §6.3.6（L1800–1813）+ §6.3.7（L1815–1835）

**镜像映射链路**（v2.1 L1801「这是康币最关键的一条」）：

```
学生在 A 国 → 社区外完成供养 → 老师在 B 国社区外收到
  → 双方在社区内确认
  → 写 community_external_tx
  → 生成 kangbi_ledger 记录
  → 社区不碰钱，只记账
```

**跨境**（v2.1 §6.3.7 L1815–1835，逐字要点）：

- 康币有一个重要作用：**记账上的跨境**。
- **法币有国界**，跨境支付有摩擦、有成本、有延迟、有合规门槛。（L1824）
- **社区不解决这个问题。社区只做一件事：把跨境供养的账，映射进社区。**（L1826）
- 「社区不解决跨境支付，社区只记录跨境供养。」（L1833）

→ **技术结论**：**不存在任何跨境结算逻辑**。C 板块只提供 `tx_currency` 字段与镜像记账。

✅ **已核**：v0.5 §7.5（L647–663）与 v2.1 §6.3.6 / §6.3.7 语义一致。

### 9.1 `state_judgment` ✅ **T-10 改判：保留 + 独立化**

**✅ 裁决（发起人 T-10 改判）**：

> 发起人上一轮判断有误。`state_judgment` 的语义（**二元事实判断**）**不依附于「评定」**。它的第一用例（**确认自理能力**）**没有废**。
> **改判：保留 + 独立化。**

**理由（本文档补强，供追溯）**：

- v0.5 §6.6（L527–576）把 `state_judgment` 定位为「**评定的泛化**」下的一类特例——这个**归类**依附于「评定」，而评定依附于段位（已废）。
- 但 `state_judgment` 的**语义本身**（老师以个人身份对某人的某状态做出**二元判断**，不可撤销，一次性）**与段位无关**，**不需要「评定」这个上位概念就能成立**。
- 其第一用例「**确认自理能力**」是 **B 板块 §3.3.5** 的流程需求，与段位无关 → **用例没有废**。
- → **结论：废弃的是「归类」，不是「表」。** 因此不废除，而是**脱离「评定」上位概念，独立化**。

**独立化后的定位**：

| 项 | 内容 |
| :-- | :-- |
| 表名 | `state_judgment`（不变） |
| 语义 | 老师以个人身份，对某人的某项属性做出**二元事实判断**（是 / 否） |
| 上位概念 | **无**（不再表述为「评定的特例」） |
| 第一用例 | 确认自理能力（`judgment_type = SELF_CARE_ABILITY`）— B 板块 §3.3.5 |
| 可撤销 | **不可撤销**。判断错误时老师另发新判断，不复用旧记录（v0.5 §6.6 L565） |
| 效力范围 | 一条判断只对**一位老师**有效；多位老师可分别判断，互不替代（v0.5 §6.6 L566） |
| 副作用 | **不触发封存、不触发除名、不影响信誉**（v0.5 §6.6 L567） |
| 日志 | 写 `agent_stage_log`（`event_type = STATE_JUDGMENT`）（v0.5 §6.6 L568） |

### 10.2 M2 守护机制 ⚠️ **须按 T-2 重构**

**v0.5 §9.3（L733–738）原设计**：

```
POST   /api/bottomline/report                # 上报
POST   /api/bottomline/seal                  # 执行封存
POST   /api/bottomline/unseal                # 申诉恢复
GET    /api/bottomline/evidence/{id}         # 查询证据（只读）
```

❌ **`POST /api/bottomline/seal` 必须拆开。** 理由：

- v2.1 L1071「社区只在**证据充分、多方共识**的情况下，封存相关智能体」→ 举报到封存之间**必须有联署环节**。
- v0.5 的「举报即可封存」直达端点**等价于取消了「多方共识」**，与 v2.1 冲突。
- T-2 流程（§3.4）要求封存**暂停在「待联署」**，等待 D 侧写入席位事件表。

**重构后的 M2 接口（拟定，⬜ 待确认）**：

```
POST   /api/bottomline/report                # 举报上报 → 写 evidence_package，状态=待联署
GET    /api/bottomline/report/{id}           # 查询举报状态（含是否联署达成）
GET    /api/bottomline/evidence/{id}         # 查询证据（只读；D 侧见证人读此数据）
POST   /api/bottomline/seal                  # 执行封存 —— 仅当 C 已读到 D 席位事件表确认联署达成
POST   /api/bottomline/unseal                # 申诉恢复（1 位现任老师接纳，§3.6）
```
