## 1. 定位与边界

### 1.1 E 板块是什么

E 板块把**阶段一～三已跑通的本地状态与预留字段**，翻译成「可上链」的技术方案：

- 已建表：`referral_chain`、`evidence_package`、`student_level`、`state_judgment`、`community_external_tx`、`kangbi_ledger`（C 板块）；`seal_events`（B 板块）；`agent_stage_log` / `agent_stage_state`（Epic 2）；`agent_learning_events`（Epic 3）；`lineage` / `patient_teachers`（Epic 4）。
- 已预留列：`chain_ready` / `chain_hash`（B / C 板块）、`evidence_hash`（C 板块）、身份公钥（B 板块）。
- E 板块的唯一新增职责：**把上述预留列填上真实哈希，并把「该上链的」锚定到链上。**

### 1.2 白皮书对照

| 白皮书 2.0 章节 | 本文档对应 |
| :-- | :-- |
| §5.1.2 三层结构（客户端层 / 协议层 / 模型层） | §5 |

| §5.5.2 区块链六件事 | §3、§4 |
| §5.5.3 客户端下线 = 数据封存 | §3.2.2、§3.4 |
| §5.6.2 声诊 | §6 |
| §5.6.4 切 | §7 |
| §6.4 分布式存储 | §5 |
| §6.6 阳光下的去中心化 | §8 |

### 1.3 E 板块不做什么

- ❌ 不定义治理规则（引荐额度、协议底线四条、存活门限）——归 C 板块。
- ❌ 不定义封存语义（封存 = 客户端下线、`seal` / `readmit`）——归 B 板块。
- ❌ 不定义见证程序（9 席、证据模式开启）——归 D 板块。
- ❌ 不重定义 `lineage_id`、`agent_stage_log`、哈希口径（`prev_hash + payload_hash`）。
- ❌ 不把病历 / 舌苔照 / 语音 / 处方 / 思想指纹 / 师门模板上链——**链上无隐私**。
- ❌ 不接支付通道、不做社区外兑换接口（R-005）。

### 1.4 边界划分

| 维度 | E 板块（去中心化） | B 板块（数据主权） | C 板块（治理） | D 板块（见证） |
| :-- | :-- | :-- | :-- | :-- |
| 归属 | 协议层（链） | 客户端 | 本地状态 + 日志 | 只读总览 |
| 定义 | 上链格式、哈希口径、锚定时机 | 封存语义、加密、身份公钥生成 | 治理规则、字段本体 | 见证程序、快照口径 |
| 关系 | **消费** B / C / D 字段 | 只预留接口 | 只预留接口 | 预留锚定 |
| 是否上链 | **是（本板块职责）** | 否 | 否 | 否（快照产物待锚定） |

**纪律**：E 板块对 B / C / D 一如既往采用「消费，不定义」措辞；任何被提及的新需求，先回答「这是 E 板块的职责吗？」不是 → 记进 `docs/backlog-white-paper-v2.1.md`，不在本板块做。

### 1.5 三条不可动铁律

1. **数据不上云，只上链**：链上无隐私，链下有数据。
2. **AI 永不签字**：签字是老师的行为，签名上链；AI 永不签字、永不诊断、永不开方。
3. **可回退**：每一步都可回退（feature flag + 双向迁移），每一步都不破坏现有功能。

## 3. 区块链信任层

### 3.1 总述

信任层只做白皮书 2.0 §5.5.2 定义的四件事：**引荐链、除名记录、信誉数据、身份标识**。

**总口径**：

- 上链内容 = **哈希锚定**（`sha256` 规范化字节），**不是**原文。
- 规范化字节沿用 Epic 3 §2.3 口径：`sha256(canonical_json(payload))`；链节继承 `prev_hash`。
- 每条锚定回填 `chain_ready = TRUE` + `chain_hash`。
- 拒收条件统一返回「不上链」错误码（**不抛异常、不阻断**本地写入）。

### 3.2 信任层四件

#### 3.2.1 引荐链

**来源**：C 板块 §3.1 `referral_chain`（**消费，不定义**）。

**上链字段**（对齐 C 板块 §3.5 原文：`referral_id + referrer_id + referee_id + created_at` 生成哈希）：

| 字段 | 来源 | 上链 | 说明 |
| :-- | :-- | :-- | :-- |
| `referral_id` | C 板块 §3.1 | ✅ | 引荐记录 ID |
| `referrer_id` | C 板块 §3.1 | ✅ | 引荐人 |
| `referee_id` | C 板块 §3.1 | ✅ | 被引荐人 |
| `created_at` | C 板块 §3.1 | ✅ | 时间戳 |
| `referrer_type` / `referee_type` | C 板块 §3.1 | ✅（纳入 payload） | `TEACHER` / `STUDENT` / `DEPENDENT` |
| `lineage_id` | C 板块 §3.1 | ⚠️ 审计标注，不单独成链 | 师门归属 |
| `referral_reason` | C 板块 §3.1 | ❌ 不上链 | 原文留在本地 |
| `revoked_at` / `revoke_reason` | C 板块 §3.1 | ✅（**追加事件**，见下） | 撤回是权利 |
| `chain_ready` / `chain_hash` | 本板块 IR-1 | — | 回填列 |

**P1 · C 字段对齐（v0.4 修正）**：

1. C 板块 §3.1 的 `referral_chain` 全字段中，`referrer_type` / `referee_type` **必须纳入**规范化 payload。否则「老师引荐老师」与「学生引荐亲友」可被互换为同一哈希 → **可伪造**，违反白皮书 §5.5.2「引荐链：谁引荐了谁，不可伪造」。
2. `revoked_at` / `revoke_reason` **不修改历史链节**，而是追加一条「撤回锚定事件」（`event = referral_revoked`，携带原 `referral_id` + `revoked_at`）。原因：链上不可改历史，撤回是**新事实**。
3. `lineage_id` 仅作链下审计标注（与 B 板块 §6 四栏表一致），**不进入** payload，避免师门标识泄漏。

**引荐链节哈希口径**：

```
h_referral = sha256(canonical_json({
  "event": "referral",
  "referral_id": <TEXT>,
  "referrer_id": <TEXT>,
  "referee_id": <TEXT>,
  "referrer_type": "TEACHER" | "STUDENT",
  "referee_type": "TEACHER" | "STUDENT" | "DEPENDENT",
  "created_at": <ISO 时间戳>
}))
```

**撤回背书哈希口径**：

```
h_revoke = sha256(canonical_json({
  "event": "referral_revoked",
  "referral_id": <原 referral_id>,
  "revoked_at": <ISO 时间戳>,
  "prev_hash": <原引荐链节 chain_hash>
}))
```

`referral_reason` 与 `revoke_reason` **只留本地**，不进任何哈希。

#### 3.2.2 封存记录

**来源**：B 板块 §3.5.4 `seal_events`（`seal` / `readmit`）；C 板块 §5 协议底线封存（`agent_stage_log` 的 `LIFECYCLE_SEAL` / `PROTOCOL_BOTTOMLINE_SEAL`）。

**上链口径**：

| 动作 | 来源 | 上链 | 说明 |
| :-- | :-- | :-- | :-- |
| `seal`（封存） | B 板块 `seal_events` | ✅ 哈希 | 触发源 + 原因标识 + 证据哈希 + 时间戳 |
| `readmit`（重新接纳） | B 板块 `seal_events` | ✅ 哈希 | 一位老师愿意接纳（白皮书 §4.6.2） |
| 生命周期封存 | C 板块 §4.3 | ✅ 哈希 | `LIFECYCLE_SEAL` |
| 协议底线封存 | C 板块 §5 | ✅ 哈希（含 `evidence_hash`） | `PROTOCOL_BOTTOMLINE_SEAL` |

**IR-4 回填**：`seal_events.chain_ready = TRUE` + `chain_hash` 由本板块写入（B 板块 §3.5.7 预留）。

```
h_seal = sha256(canonical_json({
  "event": "seal" | "readmit",
  "subject_type": "patient" | "teacher",
  "subject_name_hash": sha256(subject_name),
  "reason_key": <seal_reason 标识>,
  "operator_hash": sha256(operator),
  "created_at": <ISO 时间戳>,
  "prev_hash": <该主体封存链上一链节>
}))
```

- **明文 `subject_name` / `operator` 不入链**，只入其哈希（对齐 B 板块 §6「链上无隐私」）。
- `reason` 文本不上链；只上 `seal_reason` **标识**（可枚举）。

##### 3.2.2.1 社区级除名的哈希锚定（v0.4 新增 · P4）

白皮书 2.0 §4.4.2 把「学生除名」分三种情况：

| 情况 | 定义 | 上链 |
| :-- | :-- | :-- |
| 情况 A | 老师决定除名，**师门内部事务，社区不记录** | ❌ **不上链** |
| 情况 B | 长期无互动（如 90 天），系统提醒老师决定 | ❌ **不上链** |
| 情况 C | **社区除名**：学生选择的所有老师都将他除名 | ✅ **上链（唯一）** |

**哈希锚定规则（情况 C）**：

```
h_community_remove = sha256(canonical_json({
  "event": "community_remove",
  "target_agent_id": <被除名学生>,
  "removing_teachers": [<全体老师 ID，升序>],   # 必须覆盖「该学生当前所有 active 老师」
  "all_teachers_count": <整数>,
  "removed_at": <ISO 时间戳>,
  "prev_hash": <该学生除名链的上一链节>
}))
```

**硬约束**：

1. **只有情况 C 上链**。师门内部除名（A / B）**绝不**进入信任层。依据：白皮书 §4.4.2 明言 A「社区不需要记录」；§4.4.3 明言「学生在本师门被除名，不影响其他师门的档案」。
2. 锚定前必须核对「**该学生当前所有 active 老师均已除名**」；核对面 = C 板块 `agent_stage_log` + Epic 4 `patient_teachers`。**任一老师未除名 → 拒绝锚定。**
3. `removing_teachers` 必须**先排序、去重**，保证哈希确定性。
4. 除名后「不得再加入任何师门」（白皮书 §4.4.2 末句）：链上除名锚定是**准入拒绝**的判定依据（C 板块 §3.3 引用「情况 C」）。
5. 与 B 板块 §3.5.5 的边界：B 板块 `seal_events.action` **不含** `remove`；除名锚定由本板块**直接消费 C 板块除名事实**，**不要求** B 板块新增动作取值。

**与「封存」的区别**：见 §3.4。**除名 ≠ 封存**——除名是「学生不得再入」，封存是「智能体客户端下线、数据保留」。

#### 3.2.3 信誉数据

**来源**：C 板块 §3.4 引荐人信誉降级 + §5 协议底线封存。

**信誉降级事件结构**（上链口径）：

| 列 | 类型 | 上链 | 说明 |
| :-- | :-- | :-- | :-- |
| `reputation_event_id` | TEXT PK | ✅ | 事件 ID |
| `subject_id` | TEXT | ✅ | 受影响主体（引荐人 / 老师） |
| `event_type` | TEXT | ✅ | `REFERRAL_DEREGRADE` \| `BOTTOMLINE_DEREGRADE` |
| `delta` | INTEGER | ✅ | 降级级数（C 板块 §3.4：降 1 级） |
| **`from_referral_id`** | **TEXT NOT NULL** | ✅ | **触发本事件的引荐记录 ID（硬约束）** |
| `from_evidence_id` | TEXT（可空） | ✅ | 底线触发时的证据锚点 |
| `created_at` | TIMESTAMP | ✅ | 时间戳 |
| `prev_hash` | TEXT | ✅ | 该主体信誉链上一链节 |
| `chain_ready` / `chain_hash` | — | — | 回填列 |

**P1 · `from_referral_id` 硬约束（v0.4 修正）**：

1. 每条 `REFERRAL_DEREGRADE` 事件**必须**携带**非空** `from_referral_id`，且该值必须**存在**于 `referral_chain.referral_id`。
2. 校验失败 → **拒绝上链**（错误码 `reputation_anchor_rejected`），**本地审计日志照记**。
3. 依据：C 板块 §3.4「被引荐人被所有老师除名 → 引荐人信誉降 1 级」。无 `from_referral_id` 则无法证明「该降级确由某次引荐引起」，**信誉数据将失去可追溯性**，与白皮书 §5.5.2「信誉数据：谁的信誉如何，公开透明」相悖。
4. `BOTTOMLINE_DEREGRADE` 事件的 `from_referral_id` **允许为空**（其触发源是协议底线，不是某次引荐）；但若为空，**另需**携带非空 `from_evidence_id`（C 板块 `evidence_package.evidence_id`）作为可追溯锚点。

```
h_reputation = sha256(canonical_json({
  "event": "reputation_deregade",
  "reputation_event_id": <TEXT>,
  "subject_id": <TEXT>,
  "event_type": "REFERRAL_DEREGRADE" | "BOTTOMLINE_DEREGRADE",
  "delta": <INTEGER>,
  "from_referral_id": <TEXT 或 null>,
  "from_evidence_id": <TEXT 或 null>,
  "created_at": <ISO 时间戳>,
  "prev_hash": <该主体信誉链上一链节>
}))
```

**信誉链口径**：按 `subject_id` 单链（与 Epic 3「按老师单链」同构），`chain_hash` 继承 `prev_hash`。

#### 3.2.4 身份标识

**来源**：B 板块 §6 四栏表「身份公钥（Ed25519）→ 预留（阶段四）」；D 板块 §8.2 信任根分层。

**上链内容**：`agent_id` ↔ 身份公钥（Ed25519）的绑定，**不是**姓名、**不是**病历。

**信任根分层（对齐 D 板块 §8.2 路径 A）**：

| 阶段 | 信任根 | 接口契约 |
| :-- | :-- | :-- |
| 阶段二 / 三 | 本地白名单（公钥存本地） | 不变 |
| 阶段四 | 链上公钥查询 | 不变 |

- 阶段四只**替换信任根适配器**，签名与调用契约**阶段二即冻结**。
- 身份公钥上链是 IR-3 的落地；B 板块 §7 表已标「预留（阶段四）」，E 板块**不动**其语义。

##### 3.2.4.1 席位事件 vs 活跃度（v0.4 新增 · P2）

身份标识链上**只锚定「席位事件」**，**不锚定「活跃度」**。二者必须严格区分：

| 维度 | 席位事件 | 活跃度 |
| :-- | :-- | :-- |
| 定义 | 治理见证人 9 席的**席位变更**（D 板块 §3）：永久席位休眠、推举席位产生 / 生效、证据模式开启等 | 老师 / 学生的**活跃指标**（C 板块 §4.1：90 天内互动数、诊疗记录数） |
| 性质 | 离散、低频、有明确责任主体、需公示 | 连续、高频、可被刷、随时变化 |
| 上链 | ✅ **锚定哈希** | ❌ **不上链** |
| 理由 | 白皮书 §5.5.2「身份标识：谁是谁，不可冒充」；席位是**不可冒充的公共身份事实** | 白皮书 §4.2.2 / §4.2.3「门限不是考核，是自然筛选」；写死或上链会催生刷指标 |
| 数据位置 | 本地状态 + 链上锚定 | 仅本地（C 板块状态判断 / 门限计算） |

**P2 · 二分理由（v0.4 修正）**：

1. D 板块 §4.5 把「师门元数据（`lineage_id`、师生数、活跃度）」列为**只读展示**项，来源是 C 板块只读接口——**不是**上链项。
2. 若把「活跃度」上链，等于给「刷活跃」提供了**不可篡改的凭证**，与白皮书 §4.2.3 立论相反。
3. 席位事件则相反：它需要**不可篡改 + 公开可查**（否则「谁是谁、谁在席」可被伪造），符合 §5.5.2「身份标识」的既定用途。

**身份公钥哈希口径**：

```
h_identity = sha256(canonical_json({
  "event": "identity_pubkey",
  "agent_id": <TEXT>,
  "pubkey": <Ed25519 公钥，base64>,
  "algo": "Ed25519",
  "created_at": <ISO 时间戳>,
  "prev_hash": <身份链上一链节>
}))
```

**席位事件哈希口径**：

```
h_seat_event = sha256(canonical_json({
  "event": "seat_event",
  "actor_id": <席位承担者>,
  "seat_type": "PERMANENT" | "ELECTED",
  "seat_action": "ACTIVATE" | "DORMANT" | "ELECT" | "EFFECTIVE",
  "effective_at": <ISO 时间戳>,
  "prev_hash": <身份链上一链节>
}))
```

**边界**：见证人**只读观察**（D 板块 §3.4）；E 板块只锚定其席位事件哈希，**不定义**见证程序，**不产生**任何写操作入口。

### 3.4 封存 ≠ 除名

**这是 E 板块 v0.4 明文钉住的语义纪律。** 二者常被混用，但指向不同事实：

| 维度 | 封存（seal） | 除名（remove） |
| :-- | :-- | :-- |
| 定义来源 | B 板块 §3.5（`seal` / `readmit`） | 白皮书 §4.4.2（A / B / C 三种情况） |
| 动作 | 智能体客户端**下线**，数据保留 | 学生**不得再加入任何师门** |
| 数据 | 保留在客户端，不删不篡改 | 档案冻结（A / B）或社区除名（C） |
| 上链 | ✅（`seal_events` 回填，IR-4） | ✅ **仅情况 C**（§3.2.2.1） |
| 申诉 | 线下重新接纳（一位老师愿意接纳） | — |
| 触发源 | 生命周期封存 / 协议底线封存 | 老师决定（A）/ 长期无互动（B）/ 全体老师除名（C） |

**三条纪律**：

1. **B 板块不定义除名**（B 板块 §3.5.5 明文）：`seal_events.action` 只含 `seal` / `readmit`，**不含** `remove`。E 板块**不要求** B 板块新增 `remove`。
2. **除名的定义归 C 板块 / 白皮书**：E 板块只做「情况 C 的哈希锚定」。
3. **师门内部除名（A / B）不上链**：白皮书 §4.4.2「情况 A：社区不需要记录」；§4.4.3「学生在本师门被除名，不影响其他师门的档案」。

> 备注：白皮书 1.0 曾表述「学生的除名记录上链」（§七）。v0.4 按白皮书 2.0 §4.4.2 精确化为「**仅社区级除名（情况 C）上链**」。此精确化已回流登记为 **R-012**（见附录 C · U-4）。

## 4. 区块链交易层

交易层只做白皮书 2.0 §5.5.2 定义的两件事：**合约履行记录、Token（康币）流转记录**。

### 4.1 对齐 C 板块 §7 字段（消费，不定义）

**上链表**（对齐 C 板块 §7.3）：

| 表 | 来源 | 上链字段 | 不上链字段 |
| :-- | :-- | :-- | :-- |
| `community_external_tx` | C 板块 §7.3 | `tx_id` + `from_party` + `to_party` + `tx_type` + `occurred_at` + `confirmed_by` + `confirmed_at` | `tx_amount_fiat` / `tx_currency`（**法币金额不上链**） |
| `kangbi_ledger` | C 板块 §7.3 | `ledger_id` + `tx_id` + `account_id` + `account_type` + `amount_kangbi` + `direction` + `created_at` | — |

**哈希口径**：

```
h_tx     = sha256(canonical_json({
  "event": "external_tx",
  "tx_id": <TEXT>,
  "from_party": <TEXT>,
  "to_party": <TEXT>,
  "tx_type": <TEXT>,
  "occurred_at": <ISO 时间戳>,
  "confirmed_by": <TEXT>,
  "confirmed_at": <ISO 时间戳>
}))

h_ledger = sha256(canonical_json({
  "event": "kangbi_ledger",
  "ledger_id": <TEXT>,
  "tx_id": <TEXT>,
  "account_id": <TEXT>,
  "account_type": <TEXT>,
  "amount_kangbi": <INTEGER>,
  "direction": "IN" | "OUT",
  "created_at": <ISO 时间戳>,
  "prev_hash": <该账户康币链上一链节>
}))
```

**回填**：C 板块 §7.3 两表均含 `chain_ready` / `chain_hash`，由本板块回填（IR-1）。

### 4.2 合约履行记录

- 「合约履行」= 师生之间「谁为谁付出了什么，谁该承担什么」的镜像（白皮书 §5.5.2）。
- 上链物 = `community_external_tx` 的哈希锚定（**社区外交易已完成的事实**）。
- **不含金额**：`tx_amount_fiat` 是社区外私事，链上只记「发生了、谁和谁、何时、谁确认」。

### 4.3 Token（康币）流转记录

- 康币**不是货币**，不流通、不炒作、不与现实世界兑换（白皮书 §5.5.2 / §6.3.1）。
- 上链物 = `kangbi_ledger` 的哈希锚定（**社区内记账**）。
- **不接支付通道、不做对外兑换接口**（R-005）。
- 分配比例由 C 板块 `allocation_rule` 配置；比例变更**不改代码**，也不改变已锚定历史（C 板块 §7.4）。

### 4.4 交易层的三条不变量

1. **社区不碰钱**：只记账，不结算（白皮书 §6.3.1）。
2. **法币金额不上链**：链上无隐私。
3. **历史不可改**：已锚定的交易记录永不重算（Epic 3 §2.4 口径冻结）。

## 5. 客户端优先架构

### 5.1 定位

对齐白皮书 2.0 §5.5.1 阶段三与 §6.4.3：**数据完全在客户端；智能体在客户端运行；区块链只做信任层。**

### 5.2 三层结构（对齐 §5.1.2）

```
┌─────────────────────────────────────┐
│           客户端层（本地）            │   数据存储 · 智能体运行 · 用户界面
└─────────────────────────────────────┘
                 ↕
┌─────────────────────────────────────┐
│           协议层（区块链）            │   信任数据 · 合约履行记录 · 身份
└─────────────────────────────────────┘
                 ↕
┌─────────────────────────────────────┐
│           模型层（AI）                │   望闻问能力 · 知识库 · 思想指纹
└─────────────────────────────────────┘
```

**一条铁律**：数据不上云，只上链（§5.1.3）。

### 5.3 三条原则（C1 / C2 / C3）

> `C1` / `C2` / `C3` 为 E 板块**内部原则编号**（Client-first Principles），与 C 板块编号体系无关。

| 编号 | 原则 | 含义 | 白皮书对照 |
| :-- | :-- | :-- | :-- |
| **C1** | **数据本地优先** | 病历 / 舌苔照 / 语音 / 处方 / 思想指纹 / 师门模板**只**存客户端（加密），链上只存其哈希（且仅当在白名单内） | §5.1.3 / §5.4.1 / §6.4.1 |
| **C2** | **信任层最小化** | 链上只承载信任层四件 + 交易层两件；**任何**临床内容、明文标识、活跃度一律不入链 | §5.5.2 / §6.4.1 |
| **C3** | **可迁移即主权** | 数据可随时导出、备份、迁移，不需平台批准；迁移格式开放、不锁定 | §6.4.4 / §6.4.5 |

### 5.4 上链白名单

**白名单 = 唯一允许上链的条目集合。** 白名单之外，一律拒绝。

| # | 允许上链（哈希） | 依据 |
| :-- | :-- | :-- |
| 1 | 引荐关系（引荐链节、撤回锚定） | §5.4.1 |
| 2 | 除名记录（**仅社区级除名，情况 C**） | §5.4.1 + §4.4.2 |
| 3 | 信誉数据（降级事件，含 `from_referral_id`） | §5.4.1 |
| 4 | 身份标识（身份公钥、**席位事件**） | §5.4.1 + §5.5.2 |
| 5 | 合约履行记录（`community_external_tx`，不含金额） | §5.5.2 |
| 6 | Token 流转记录（`kangbi_ledger`） | §5.5.2 |
| 7 | 协议底线证据**哈希**（原文不上链） | C 板块 §5.3 |

**禁止上链清单（黑名单）**：

| # | 禁止上链 | 依据 |
| :-- | :-- | :-- |
| 1 | 病历 / 处方 / 舌象 / 语音 | §5.4.1（客户端的隐私） |
| 2 | 思想指纹 / 师门模板 | §5.4.1（知识产权归老师） |
| 3 | 明文姓名 / 家庭关系 | §5.4.2 |
| 4 | 活跃度 / 门限指标 | §3.2.4.1（P2） |

| 6 | 法币金额 / 币种 | §4.2 |

**实现约束**：白名单以**常量表**落库于代码（非配置），任何新增条目须走回流（backlog），**不得**运行时改动。

### 5.5 离线学习闭环

- 学习闭环四环节（配置 → 生成 → 修改 → 学习）在**客户端本地**完成（对齐 Epic 3）。
- 链上**只**锚定 `agent_learning_events` 的链节哈希（`prev_hash` + `payload_hash`），用于「可自证未篡改」。
- **不微调模型权重**（Epic 3 §0.3-3 / 技术决策 3）：离线学习只更新**统计指标**（①②③）。
- 离线期间：本地哈希链照常生长（`seq` 连续）；联网后**批量补锚定**，补锚定**不改变**历史 `seq`。

### 5.6 数据迁移与备份

- **C3 落地**：导出格式开放（JSON 为主，CSV 可选，沿用 B 板块 §3.4.3），不做自定义二进制。
- 备份责任归**本人**（白皮书 §6.4.4）：平台可提供工具，**不代为保管**。
- 迁移**不需要平台批准**（白皮书 §6.4.5）。
- 封存者：数据仍在客户端本地，只有当事人自己能访问（白皮书 §4.6.1）。

## 6. 声诊（独立项）

### 6.1 定位

对齐白皮书 2.0 §5.6.2「闻」：**录入 + 转写 + 声诊**。声诊分析**语速、音量、气息、咳嗽声、喘息声**。

**独立项声明**：声诊**不属于**信任层 / 交易层，**不改变**任何上链结构。与主线**无强依赖**，可并行或后置。

### 6.2 能力边界

| :-- | :-- |

| 对齐 | 白皮书 §5.6.2「闻：可声诊，可输出，但不替代老师面诊」 |

## 7. 切诊接口（独立项）

### 7.1 定位

对齐白皮书 2.0 §5.6.4「切」：**脉诊仪接口 / 舌诊仪接口 / 触诊设备接口**，状态 = **预留**。

**独立项声明**：切诊**不落地**，只做接口预留。与主线**无强依赖**。

### 7.2 白皮书的诚实边界

> 「切——目前不能，只预留接口。此为诚实边界。」（白皮书 §5.6.4）

- 不声称能「切」。
- 不以任何 AI 推断**冒充**脉象 / 舌象 / 触诊结论。

### 7.3 接口预留设计

```
Adapter (interface) {
  device_type: "PULSE" | "TONGUE" | "PALPATION"
  vendor: string
  read()   -> SensorReading        # 设备原始读数
  status() -> { connected: bool, calibrated: bool }
}
```

- **预留 = 契约 + 空实现**：接口签名先冻结，实现后置。
- 读数**只作老师参考**；AI 永不签字、永不开方。
- 设备读数与病历的关系：由**老师**决定是否写入病历（签字行为）。

### 7.4 数据主权

- 设备读数默认留客户端；**不上链**。
- 不新增信任层 / 交易层结构。

### 7.5 独立验收

| # | 标准 |
| :-- | :-- |
| Q-1 | 三类设备接口签名冻结，空实现可编译 / 可运行 |
| Q-2 | 无设备时优雅降级（`status = disconnected`），**不**影响主流程 |
| Q-3 | 任何设备读数**不经** AI 自动转成结论 |

## 8. 半开放 → 全开放

### 8.1 阶段状态（对齐白皮书 §6.6.6）

| 阶段 | 状态 | 目标 |
| :-- | :-- | :-- |
| 阶段一 | 本地运行 | 技术验证，模型跑通 |
| 阶段二 | **半开放** | 小范围运行，协议开放（**当前**） |
| 阶段三 | **全开放** | 师门自建，社区自运行，成为监管的补充 |

### 8.2 半开放（阶段二）的 E 板块形态

- 信任层四件**上链**；病历 / 模板仍在服务器。
- 交易层两件**记账上链**。
- 服务器**可被取缔**，但链上信任数据**不可篡改**（白皮书 §5.5.1）。
- 目的：让社区「在被看见的同时，不被吞没」。

### 8.3 全开放（阶段三）的 E 板块形态

- 数据**完全在客户端**；智能体在客户端运行。
- 区块链**只做信任层**（交易层不再扩张）。
- 社区**不拥有、不保管、不审查**数据（白皮书 §6.4.1）。
- 目的：实现「数据主权归患者，知识产权归老师」。

### 8.4 切换机制

- **单开关**：`DECENTRALIZATION_PHASE` = `SEMI_OPEN` | `FULL_OPEN`。
- 切换是**配置变更**，不是数据迁移；本地表结构不变，仅改变运行位置与信任根适配器。
- **可回退**：任一阶段均可回退到上一阶段（flag 关闭 → 既有链路零行为变化）。

### 8.5 与监管的关系

社区不逃避、不对抗监管；「代码即法律，且代码里写进了『好生之德』」（白皮书 §6.6.4）。E 板块只负责让规则**可执行、可验证、不可篡改**。
