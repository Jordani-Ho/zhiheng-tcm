## 1. 总述

### 1.1 阶段三目标

把白皮书 2.0 第四章（治理机制）与第六章（运营白皮书·康币部分）的规则，翻译成可执行的技术方案。本阶段完成后，社区在**本地环境**具备完整治理能力，可进入阶段四做上链与客户端优先改造。

### 1.2 五子项关系

```
引荐链（谁引荐谁）
   │
   ├──→ 存活门限（引荐进来后，活不活得下去）
   │
   ├──→ 协议底线（触碰底线，封存）
   │
   ├──→ 评定（老师评定，多师汇总）
   │
   └──→ 康币（成本分摊，镜像记账）
```

- **引荐链**是地基：其他四项都以「谁在社区里」为前提。
- **存活门限**与**协议底线**是双向筛选：门限筛「不活跃的」，底线筛「越界的」。
- **评定**与**康币**是状态记录：评定描述学生的修行状态，康币记录成本流向。

### 1.3 本阶段不做什么

- ❌ 不接支付通道
- ❌ 不做区块链上链（本阶段只做本地状态 + 本地日志）
- ❌ 不做治理见证入口（板块 D 独立，只在 §11.3 预留只读接口）
- ❌ 不做客户端优先改造（阶段四）
- ❌ 不重定义 `lineage_id`、`agent_stage_log`

## 2. 与现有系统的关系

**接口定义以 `docs/phase2-data-sovereignty-design.md` v1.1 + `docs/epic4-lineage-design-v1.md` v1 为准，C 板块不重定义。**

### 2.1 复用清单

| 现有资产 | 来源 | C 板块如何使用 |
| :-- | :-- | :-- |
| `lineage_id` | Epic 4 | 引荐链的关系标识、评定的师门归属标识 |

### 2.2 与 B 板块 B4 的封存对齐

**封存是一个动作，两个触发源。**

| 触发源 | 触发条件 | 来源 |
| :-- | :-- | :-- |
| 生命周期封存 | 老师不再活跃 / 被除名 | B 板块 B4 |
| 协议底线封存 | 触碰四条底线之一 | C 板块 §5 |

**对齐原则**：

- C 板块**不预设** B4 提供统一封存入口。
- C 板块**不自行实现**平行封存入口。
- **封存语义对齐即可**：两个触发源都指向「智能体客户端下线 + 数据保留 + 引荐链标记」。
- 具体接口**待 B4 实现阶段定**。C 板块照 B4 接口调用。

**待 B4 闭环后，C 板块照抄 B4 签名，不在本文档预设。**

**若 B4 未提供 `seal_reason` 参数**（用于区分生命周期封存 / 协议底线封存），C 板块需向 B 板块提出扩展需求，不自行实现平行封存入口。

### 2.3 与阶段四的边界

| 能力 | C 板块（本阶段） | 阶段四 |
| :-- | :-- | :-- |
| 引荐链 | 本地表 + 本地查询 | 上链，哈希不可篡改 |
| 评定 | 本地表 + 老师评定 | 上链，跨师门可验证 |
| 存活门限 | 本地定时任务 | 上链状态快照 |
| 协议底线 | 本地封存 + 哈希存证 | 哈希上链 |
| 康币 | 本地记账表 | 上链流转记录 |

**原则**：C 板块所有数据模型与 API 都**预留 `chain_ready: bool` 字段**，阶段四只补上链逻辑，不改数据结构。

## 3. 引荐链

### 3.1 数据模型

**复用 `lineage_id`，不重定义。**

```
referral_chain (
  referral_id        TEXT PRIMARY KEY,       -- 引荐记录 ID
  referrer_id        TEXT NOT NULL,          -- 引荐人 ID
  referrer_type      TEXT NOT NULL,          -- TEACHER | STUDENT
  referee_id         TEXT NOT NULL,          -- 被引荐人 ID
  referee_type       TEXT NOT NULL,          -- TEACHER | STUDENT | DEPENDENT
  lineage_id         TEXT,                   -- 复用 Epic 4，师门归属
  referral_reason    TEXT,                   -- 一句话理由（老师引荐必填）
  created_at         TIMESTAMP NOT NULL,
  revoked_at         TIMESTAMP,              -- 背书撤回时间（可空）
  revoke_reason      TEXT,
  chain_ready        BOOLEAN DEFAULT FALSE,  -- 阶段四上链标记
  chain_hash         TEXT                    -- 阶段四填充
)
```

### 3.2 老师引荐老师

**流程**：

```
现任老师 → 发起引荐 → 填写 referee_id + referral_reason
  → 写 referral_chain（referrer_type=TEACHER）
  → 老师准入（白皮书 §4.2.1）
  → 新老师建立自己的 lineage_id
```

**约束**：

- `referral_reason` 必填，一句话。
- 不得自引荐（`referrer_id != referee_id`）。
- 被引荐老师若已有 `lineage_id`，保留源流，新师门独立编号。

### 3.3 学生引荐亲友

**流程**：

```
学生 → 发起引荐 → 选择亲友类型
  ├─ 可自理者 → 老师智能体审核 → 老师审批 → 学生准入
  └─ 不能自理者/未成年人 → 直接作为被照护者（监护模式）
  → 写 referral_chain（referrer_type=STUDENT）
```

**额度限制**：

- 每位学生每年最多引荐 3 位亲友。
- 额度按自然年重置。
- 被照护者占用额度，与独立学生同等计数。

**约束**：

- 引荐人必须信誉良好（无未了结的协议底线封存）。
- 被引荐人若曾被所有老师除名，不可再入（白皮书 §4.4.2 情况 C）。

### 3.4 引荐人信誉降级

**不连坐，只降级。**

| 事件 | 引荐人影响 |
| :-- | :-- |
| 被引荐人被一位老师除名 | 无影响 |
| 被引荐人被所有老师除名 | 引荐人信誉降 1 级 |
| 被引荐人触碰协议底线 | 引荐人信誉降 1 级 |
| 引荐人主动撤回背书 | 无影响（撤回是权利） |

**信誉等级**：沿用 Epic 4 已定义的信誉模型，C 板块不重定义。

### 3.5 上链预留

本阶段只存本地。`chain_ready = FALSE`。

阶段四：`referral_chain` 的 `referral_id + referrer_id + referee_id + created_at` 生成哈希上链，`chain_hash` 回填。

## 4. 存活门限

### 4.1 指标定义

| 指标 | 定义 | 初始值 |
| :-- | :-- | :-- |
| 活跃学生数 | 90 天内有过互动的学生数 | ≥ 3 |
| 活跃度 | 90 天内的诊疗记录 + 互动次数 | ≥ 1 次/月 |

**初始值说明**：由发起人确认。**具体数值由系统自动调节**，调节算法见下。

**调节算法（框架）**：

```
门限 = base_threshold × community_factor

base_threshold:
  活跃学生数 = 3
  活跃度 = 1 次/月

community_factor:
  社区初期（老师数 < 10）：0.5（宽松）
  社区成熟期（老师数 ≥ 10）：1.0
  社区过密期（老师数 > 50）：1.5（趋严）

调节依据：
  - 社区整体活跃度
  - 老师数量
  - 学生数量
  - 资源占用情况
```

**具体系数由运营细则定义，本文只给框架。**

### 4.2 状态机

```
    [活跃]
      │
      │ 3 个月未达标
      ▼
   [不活跃]
      │
      │ 再 3 个月未达标
      ▼
    [下线]
      │
      │ 申诉：线下找到一位现任老师愿意接纳
      ▼
    [活跃]（恢复）
```

### 4.3 自动执行逻辑

**定时任务**（每日执行一次）：

```
for each 老师 in 社区:
  if 老师.状态 == 活跃:
    if 90 天未达标:
      老师.状态 = 不活跃
      写 agent_stage_log（event_type=LIFECYCLE_THRESHOLD）
  elif 老师.状态 == 不活跃:
    if 再 90 天未达标:
      老师.状态 = 下线
      调用 B4 封存接口（接口待 B4 定）
      写 agent_stage_log（event_type=LIFECYCLE_SEAL）
```

**不活跃状态下的限制**（白皮书 §4.2.2）：

- 不再出现在引荐候选列表中。
- 不再有资格引荐新老师。
- 名下学生可自由选择是否继续跟随。

### 4.4 与除名机制的关系

**门限是自然筛选，不是除名。**

| 维度 | 存活门限 | 协议底线封存 |
| :-- | :-- | :-- |
| 触发 | 不活跃 | 越界 |
| 性质 | 自然流失 | 强制封存 |
| 数据 | 保留，可恢复 | 保留，封存 |
| 申诉 | 达标即恢复 | 线下重新接纳 |

两者共用 B4 封存入口，但 `seal_reason` 不同，日志可区分。

## 5. 协议底线

### 5.1 四条底线（白皮书 §4.3.3 原文）

1. 冒充他人师承。
2. 伪造引荐链。
3. 恶意欺骗学生。
4. 恶意伤害他人。

### 5.2 封存动作定义

**与 §2.2 对齐，C 板块不预设接口。**

C 板块在触发协议底线封存时，语义上需要传入：

- 封存原因标识（区分「协议底线封存」与「生命周期封存」）
- 证据哈希（§5.3 定义）
- 触发人 ID
- 时间戳

**接口签名以 B 板块 B4 实现阶段定义为准。C 板块照 B4 接口调用，不自行实现平行封存入口。**

封存后（与生命周期封存效果对齐）：

- 智能体客户端下线，不对外服务。
- 引荐链标记异常，源流暂停可查。
- 数据保留在客户端，不删除，不篡改，不审查。

### 5.3 证据留存格式

**哈希存证 + 原文不上链。**

| 数据 | 存储位置 | 是否上链 |
| :-- | :-- | :-- |
| 证据原文 | 本地（阶段二）→ 客户端（阶段四） | 否 |
| 证据哈希 | 本地（阶段二）→ 链上（阶段四） | 是（阶段四） |

**证据包结构**：

```
evidence_package (
  evidence_id      TEXT PRIMARY KEY,
  target_agent_id  TEXT NOT NULL,
  bottomline_type  TEXT NOT NULL,  -- IMPERSONATION | FORGERY | DECEPTION | HARM
  evidence_raw     BLOB NOT NULL,  -- 原文/截图/录音，本地存储
  evidence_hash    TEXT NOT NULL,  -- SHA-256(evidence_raw + metadata)
  created_at       TIMESTAMP NOT NULL,
  chain_ready      BOOLEAN DEFAULT FALSE,
  chain_hash       TEXT
)
```

**哈希计算**：

```
evidence_hash = SHA-256(
  evidence_raw ||
  target_agent_id ||
  bottomline_type ||
  created_at
)
```

**原则**：

- 原文**永不上链**，只在本地/客户端。
- 哈希上链（阶段四），保证原文未被篡改。
- 验证时，本地原文重新哈希，与链上哈希比对。

### 5.4 触发流程

```
证据留存 → 调用 B 板块 B4 封存接口（接口待 B4 定）
  → 写 agent_stage_log
  → 标记 referral_chain（引荐人信誉降级）
  → 通知当事人（事后知情）
```

**开启程序**：

C 板块**不定义**治理见证人的开启程序。程序定义属 D 板块。

C 板块在需要开启证据模式时，**调用 D 板块的治理见证人开启接口**。接口定义待 D 板块闭环后补齐。

**注意**：治理见证人机制的完整设计属板块 D，本节只登记 C 板块需要调用 D 板块的接口需求，不定义其内容。

### 5.5 申诉通道

**线下重新接纳。**

```
被封存者 → 线下找到一位现任老师
  → 老师愿意接纳
  → 恢复原有封存的数据权限
  → 重新上线
```

- 社区不设申诉庭，不做审判。
- 一位老师愿意接纳，就够了。
- 这位老师，为重新入社区者背书。

**技术实现**：

```
unseal_agent(
  agent_id,
  sponsor_teacher_id,   -- 愿意接纳的老师
  timestamp
) -> unseal_record
```

接口签名以 B 板块 B4 实现阶段定义为准。

## 6. 评定（段位与状态判断）

### 6.1 五段定义（白皮书 §2.5.5 + §4.5.2 原文）

| 段位 | 名称 | 状态 |
| :-- | :-- | :-- |
| 一段 | 知常 | 知道什么是正常——了解节气、作息、身体的基本信号 |
| 二段 | 守常 | 能守住正常——开始养成习惯，能觉察偏离 |
| 三段 | 安常 | 安于正常——习惯成自然，不再需要刻意提醒 |
| 四段 | 达常 | 通达正常——能灵活应对变化，知道何时该调整 |
| 五段 | 传常 | 传递正常——能帮助他人，可引荐亲友，可申请成为学徒 |

### 6.2 与「阶段」（Epic 2）的维度区分

**两个维度，不得混用。**

| 维度 | 阶段 | 段位 |
| :-- | :-- | :-- |
| 描述对象 | 智能体 | 学生 |
| 含义 | 智能体成长阶段 | 学生与天地相处的状态 |
| 取值 | 观察→学习→见习→助手→授权 | 一段→五段 |
| 评定者 | 系统（学习闭环） | 老师 |
| 变化频率 | 随训练进展 | 随状态升降 |

**技术约束**：

- 阶段字段：`agent.stage`（Epic 2 已定义）
- 段位字段：`student_level.level`（C 板块新增）
- 两者不得互相赋值，不得在同一 UI 组件中混淆展示。

### 6.3 数据模型

```
student_level (
  student_id       TEXT NOT NULL,
  teacher_id       TEXT NOT NULL,
  lineage_id       TEXT NOT NULL,      -- 复用 Epic 4
  level            INTEGER NOT NULL,   -- 1..5
  level_name       TEXT NOT NULL,      -- 知常/守常/安常/达常/传常
  evaluated_at     TIMESTAMP NOT NULL,
  note             TEXT,               -- 老师评定备注
  PRIMARY KEY (student_id, teacher_id)
)
```

**多师汇总**：

- 每位老师各自评定，各自一条记录。
- 学生智能体汇总展示：列出每位老师的评定，不合并、不平均。
- 学生自己的完整段位，由学生智能体汇总展示，社区不制定统一标准。

### 6.4 升降规则

- 段位可升可降。
- 状态回落，段位随之回落，不是耻辱，是如实。
- 段位下降，不触发任何处罚。
- 段位不影响学生查看档案、引荐亲友、选择老师。

**技术约束**：

- 段位变更写入 `agent_stage_log`（`event_type=LEVEL_CHANGE`）。
- 段位变更不触发封存、不触发除名、不影响信誉。

### 6.5 段位与学徒的关系

**段位与学徒是两个独立维度，不得混用。**

| 维度 | 段位 | 学徒 |
| :-- | :-- | :-- |
| 描述对象 | 学生 | 真人学徒 |
| 含义 | 学生与天地相处的状态 | 师承体系内的角色 |
| 取值 | 一段～五段 | 是 / 否 |
| 评定者 | 老师 | 老师挑选 + 学生承诺（双向） |
| 生命周期 | 可升可降，可长期停留 | 可出师成为老师，可退回学生 |
| 与另一个维度的关系 | 独立 | 独立 |

**关系说明**：

- 五段「传常」是学生段位的最高段。
- 「可申请成为学徒」是学生的一项**权利**（白皮书 §2.5.4 学生的权力），不是段位自带的**身份**。
- 一个五段学生可以选择不申请成为学徒，继续做学生。
- 一个学徒可以是三段「安常」（在学如何传道的过程中，修行状态未必到五段）。

**技术约束**：

- 段位字段：`student_level.level`（§6.3）
- 学徒身份字段：**待定**。
  - 不在 Epic 4 交付范围内。
  - 本步先登记概念区分（段位 ≠ 学徒），字段落点等实现阶段定。
  - 可能是 `agent.role` 扩展，可能是新增表，可能两者组合。本步不预判。

**五段「传常」措辞**：白皮书 2.0 定稿原文为「可申请成为学徒」。C 板块不在本板块提白皮书修订。

### 6.6 评定的泛化：状态判断

§6 前五节定义的「段位评定」是「评定」的一类特例。本节定义另一类特例：**状态判断**。

**定义**：老师以个人身份，对某人的某状态做出**二元判断**（是 / 否）。

**典型场景**：

- **确认自理能力**（B 板块 §3.3.5）：老师确认被照护者已具备自理能力。
- 其他场景待补充，本步只登记第一例。

**与段位评定的区别**：

| 维度 | 段位评定 | 状态判断 |
| :-- | :-- | :-- |
| 对象 | 学生的修行状态 | 某人的某项属性 |
| 输出 | 一段～五段（分级） | 是 / 否（二元） |
| 可升降 | 可升降 | 不可（事实性判断） |
| 数据结构 | `student_level` | `state_judgment`（新增） |
| 时效 | 持续有效，可更新 | 一次性，不可撤销 |

**数据模型**：

```
state_judgment (
  judgment_id      TEXT PRIMARY KEY,
  target_agent_id  TEXT NOT NULL,      -- 被判断者
  teacher_id       TEXT NOT NULL,      -- 判断者
  lineage_id       TEXT NOT NULL,      -- 复用 Epic 4
  judgment_type    TEXT NOT NULL,      -- 当前仅：SELF_CARE_ABILITY
  judgment_result  BOOLEAN NOT NULL,   -- TRUE / FALSE
  judged_at        TIMESTAMP NOT NULL,
  note             TEXT,
  chain_ready      BOOLEAN DEFAULT FALSE,
  chain_hash       TEXT
)
```

**约束**：

- 状态判断**不可撤销**。若判断错误，老师另发一条新判断，不复用旧记录。
- 一条状态判断只对**一位老师**有效。多位老师可分别判断，互不替代。
- 状态判断不触发封存、不触发除名、不影响信誉。
- 状态判断写入 `agent_stage_log`（`event_type=STATE_JUDGMENT`）。

**与 B 板块 §3.3.5 的衔接**：

B 板块 §3.3.5「恢复自理能力」的判定流程，调用 C 板块的状态判断接口：

- `judgment_type = SELF_CARE_ABILITY`
- `judgment_result = TRUE` 时，被照护者的数据主权归还给他 / 她本人（B 板块数据主权规则）
- 具体接口调用方式由 B 板块设计定义，C 板块只提供状态判断数据模型

## 7. 康币

### 7.1 定位重申（白皮书 §5.5.2.2 + §6.3.1）

**社区币，不碰钱，只记账。**

- 不是货币，不流通，不炒作。
- 是成本分摊的单位，是社区外交易的镜像映射。
- 与现实世界没有支付兑换接口，也不打算有。
- 阶段三明确：无链上价值。

### 7.2 成本类型（白皮书 §6.3.2 原文）

| 成本类型 | 承担方 | 换算方式 |
| :-- | :-- | :-- |
| 老师时间 | 学生 | 按诊疗时长、复杂程度换算 |
| 智能体算力 | 学生 | 按 API 调用量、模型规模换算 |
| 电力 | 平台 + 老师 | 按服务器能耗分摊 |
| 存储 | 学生 | 按数据量、存储时长换算 |
| 网络交换 | 平台 + 老师 | 按带宽占用分摊 |

### 7.3 记账模型

**社区外交易 → 社区内映射 → 生成康币记录。**

```
community_external_tx (
  tx_id            TEXT PRIMARY KEY,
  from_party       TEXT NOT NULL,      -- 学生（社区外）
  to_party         TEXT NOT NULL,      -- 老师（社区外）
  tx_type          TEXT NOT NULL,      -- OFFERING | INFRASTRUCTURE
  tx_amount_fiat   DECIMAL,            -- 社区外法币金额（仅记录，不结算）
  tx_currency      TEXT,               -- 法币币种
  occurred_at      TIMESTAMP NOT NULL,
  confirmed_by     TEXT NOT NULL,      -- 社区内确认人
  confirmed_at     TIMESTAMP NOT NULL
)

kangbi_ledger (
  ledger_id        TEXT PRIMARY KEY,
  tx_id            TEXT NOT NULL,      -- 关联 community_external_tx
  account_id       TEXT NOT NULL,      -- 老师/平台/公共池
  account_type     TEXT NOT NULL,      -- TEACHER | PLATFORM | PUBLIC_POOL
  amount_kangbi    DECIMAL NOT NULL,
  direction        TEXT NOT NULL,      -- IN | OUT
  created_at       TIMESTAMP NOT NULL,
  chain_ready      BOOLEAN DEFAULT FALSE,
  chain_hash       TEXT
)
```

**原则**：

- 社区不碰钱，只记账。
- 社区外交易由当事人自行完成，社区内只做确认与映射。
- 康币记录不可兑换、不可转让、不可用于社区外。

### 7.4 分配规则

| 流向 | 比例 | 说明 |
| :-- | :-- | :-- |
| 老师 | 主要部分 | 老师的时间与智慧 |
| 平台 | 小部分 | 基础设施维护 |
| 公共池 | 小部分 | 用于社区公共事务，如志愿团队 |

**具体比例由社区共识确定，本章不写死。** 技术实现预留 `allocation_rule` 配置表，比例变更不改代码。

### 7.5 社区外交易的镜像映射

**社区不解决支付，只记录供养。**

```
学生在 A 国 → 社区外完成供养 → 老师在 B 国社区外收到
  → 双方在社区内确认
  → 写 community_external_tx
  → 生成 kangbi_ledger 记录
  → 社区不碰钱，只记账
```

**跨境场景**：

- 社区不解决跨境支付问题。
- 社区只把跨境供养的账，映射进社区。
- 具体实现方式，由运营细则定义，技术白皮书保留入口。

### 2.3.6 老师确认（上位抽象）

附在 §2.3 后（本附录补充说明，正文修订见下）：

「老师确认」不是独立动作，是**上位抽象**：

> **老师作为最终决定权主体，对任一事项做出「同意 / 不同意」的动作。**

它涵盖 C 板块所有「老师 × 某动作」原语的共同语义：

| 具体原语 | 在「确认」语义下的表现 |
| :-- | :-- |
| 引荐 | 老师确认「此人可入社区」 |
| 背书 | 老师确认「此人的医德医术」 |
| 签字 | 老师确认「此病历 / 方剂可生效」 |
| 评定 | 老师确认「此人 / 此状态为 X」 |
| 审批 | 老师确认「此请示可执行」 |
| 接纳 | 老师确认「此被封存者可重新入社区」 |

**技术约束**：

- 「老师确认」是描述性概念，不新增数据结构。
- 不新增 API。
- 不替代六个具体原语。
- 具体动作仍按各自章节定义执行。

**来源**：B 板块 v1.1 需求，C 板块 v0.5 采纳。
