### 1.2 模块依赖图

```

   │
   ├──→ M2 只读入口（依赖 M1 鉴权 + C §11.3 接口定义）
```

### 1.3 建议顺序

| 序 | 模块 | 依赖 | 理由 |
| :-- | :-- | :-- | :-- |
| 1 | M4 哈希快照 | A §2.3（已冻结） | 地基，独立，不被任何模块阻塞 |
| 2 | M1 席位机制 | 无 | 独立，M2/M3 依赖 |
| 3 | M2 只读入口 | M1 + C §11.3 接口定义 | 依赖席位鉴权；C 接口定义已存在 |
| 4 | M3 证据模式 | M1 + M2 | 依赖前两者 |
| 5 | M6 安全合规 | M1/M2/M3 | 贯穿，随各模块推进 |
| 6 | M5 接口契约 | 横切 | 随各模块推进 |

**先 M4 后 M1 的理由**：M4 依赖已冻结的 Epic 3 口径，不引入新依赖，可立即启动；M1 是 D 板块自有逻辑，无外部依赖，紧随其后。

### 3.1 与 C 板块的接口关系

**C 骨架 §3.2 现状**：C 板块登记「待 D 定：治理见证人开启接口签名」，隐含「C 调用 D」的语义。

**D 板块立场**：C 与 D 之间**无任何直接调用**。是**拉模式**，不是**推模式**。

**实际接口关系**：

1. C 触发治理动作（除名 / 引荐 / 底线）
2. C 写入自己的本地治理事件表
3. D 通过 C v0.5 §11.3 四个只读接口**拉取**
4. D 侧见证人（永久席位 / 推举席位联署）自行决定是否开启证据模式

**语义要点**：

- 无直接调用：C 不调用 D，D 不调用 C
- C 只写自己的本地表
- D 单向只读消费
- 完全符合白皮书 2.0 §4.3「天然围墙」精神

**连锁修正（跨板块待办）**：

C 骨架 §3.2 应撤销「调用 D 开启接口」的表述，改为「D 消费 C 的治理事件表」。C 骨架升 v1.0 时一并处理。
