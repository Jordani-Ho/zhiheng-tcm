## 1. 总纲

### 1.1 核心原则

阶段二「数据主权落地」围绕一条主线：**让数据真正归本人。**

- 患者数据归患者。
- 老师思想归老师。
- 被照护者数据归被照护者。
- 平台不拥有数据，不拥有知识，只提供协议、身份、路由、存储、结算。

### 1.2 一条铁律

**数据不上云，只上链（阶段四）。链上无隐私，链下有数据。**

阶段二不实际上链。所有「上链」相关项均标注为**接口预留，阶段四落地**。

### 1.3 五个子项

| 编号 | 子项 | 一句话定位 |
| :---- | :---- | :---- |
| 1 | 数据加密存储 | 患者数据私钥持有 |
| 2 | 思想指纹加密 | 老师思想可署名、可带走 |
| 3 | 监护模式 | 被照护者数据独立存储、独立归属 |
| 4 | 数据导出 / 迁移 | 格式开放、不锁定 |
| 5 | 数据封存 | 客户端下线 = 数据封存 |

## 2. 全局约束：双主权模型

### 2.1 两个主权

| 主权 | 归属 | 对象 |
| :---- | :---- | :---- |
| 数据主权 | 患者（或被照护者） | 姓名、家庭关系、症状、舌象、语音、病历、处方 |
| 知识产权 | 老师 | 从原材料中抽象出的知识（思想指纹、师门模板） |

### 2.2 为什么两者不矛盾

因为**对象不同**。

- 患者拥有的是**不可抽象、只属于个体的标识**（姓名、家庭关系）与**天地呈现**（性别、出生时间、症状、舌象）。
- 老师拥有的是**从原材料中提炼的智慧**。

患者有权删除「张三」这个标识，但不能删除「五行属火宜清热」这个知识。

### 2.3 平台的位置

- 平台不拥有知识，不拥有数据。
- 平台只提供协议、身份、路由、存储、结算。
- 知识归老师，数据归患者，师门拥有师承链。

## 3. 五子项详细设计

### 3.1 子项 1：数据加密存储

#### 3.1.1 是什么

患者的所有原始数据在客户端以加密形式存储。私钥由患者持有，不离开客户端。

#### 3.1.2 数据分类

| 数据类型 | 内容 | 加密方式 |
| :---- | :---- | :---- |
| 个体标识 | 姓名、家庭关系 | 单独加密（字段级） |
| 生物特征原始数据 | 舌象、语音 | 单独加密（字段级） |
| 天地呈现 | 性别、出生时间、症状 | 随主密钥加密 |
| 诊疗记录 | 病历、处方 | 随主密钥加密 |

#### 3.1.3 密钥层次

```
助记词（BIP-39，12/24 词，用户自持）
   │  Argon2id 派生（熵拉伸，抗暴力破解）
   ▼
种子（Seed，64 字节）
   │  BIP-32 派生（分层确定性密钥树）
   ▼
扩展私钥树（xprv）
   │
   ├── 根密钥（即主密钥，Master Key）
   │       │
   │       ├── HKDF-SHA256 派生 ──→ 主数据密钥（加密「随主密钥」字段）
   │       │
   │       └── AES-256-GCM 加密存储 ──→ 字段私钥包（Field Key Bundle）
   │                                       ├── 姓名私钥（含 tombstone）
   │                                       ├── 家庭关系私钥（含 tombstone）
   │                                       ├── 舌象私钥（含 tombstone）
   │                                       └── 语音私钥（含 tombstone）
   │
   └── 预留：按师门派生的子密钥（阶段四及以后）
```

**派生链说明**：

1. **BIP-39 只负责助记词 ↔ 种子的编码**，不直接派生密钥。
2. **Argon2id** 对种子做熵拉伸。
3. **BIP-32** 派生**分层确定性密钥树**（xprv/xpub），不是单值。根节点即主密钥。
4. **保留 BIP-32 的目的**：为将来按师门派生独立子密钥预留空间。
5. **主密钥**是整个密钥层次的根，助记词恢复的是主密钥。

#### 3.1.4 字段私钥包与 tombstone

字段私钥包是一个加密结构，由主密钥加密存储。每个字段条目包含：

```json
{
  "field_id_hash": "sha256(field_id)",
  "key_id": "field-key-name-v1",
  "status": "active" | "deleted",
  "last_blob_version": 3,
  "encrypted_key_material": "...",
  "deleted_at": null | "2026-10-01T...",
  "tombstone_signature": "..."
}
```

**关键设计**：

- **field_id 用哈希**（`sha256(field_id)`）：
  - 防止 tombstone 泄漏「某患者删除过哪个字段」这一事实。
  - 攻击者拿到字段私钥包，看不出删的是姓名还是舌象。
  - 只有持有主密钥者，能用已知 field_id 计算哈希后定位条目。
- **删除语义 = tombstone 标记**：
  - 删除「姓名」标识 = 将姓名条目改为 `{status: "deleted", deleted_at: ..., last_blob_version: N}`。
  - 不物理移除条目。
  - 主密钥与其他字段不受影响。
- **重放攻击防护**：
  - 任何 `version ≤ last_blob_version` 的字段 blob 一律拒绝解密。
  - 攻击者即使拿到旧版 ciphertext，也无法回放。
- **物理清理（可选）**：
  - 用户可发起「彻底删除」，清除所有历史版本的 ciphertext。
  - 保留 tombstone 记录，避免版本号复用。

#### 3.1.5 存储位置

- 客户端本地。加密存储。
- 不上云。
- 不上链。

#### 3.1.6 与白皮书的对应

§1.2、§5.4.1、§5.4.2。

### 3.2 子项 2：思想指纹加密

#### 3.2.1 是什么

老师的思想指纹以加密形式存储在客户端。老师可署名、可传承、可带走。

#### 3.2.2 思想指纹的归属与署名

- **归属**：老师个人。
- **可署名**：思想指纹与老师的身份公钥关联，署名可验证。
- **可传承**：老师不再活跃时，按「思想连续性优先」原则处理。
- **可带走**：老师可导出，迁移到其他客户端，不需要平台批准。

#### 3.2.3 抽象过程

- **归一化**：复用 `_normalize_metric_text` 对指标文本归一化。
- **剥离时机**：在归一化之后、抽象之前，剥离患者标识（姓名、家庭关系）。
- **审计方式**：源码级守护（代码审查 + 静态检查），不做运行时审计。

#### 3.2.4 密钥归属

- **密钥归老师个人所有。**
- **授权范围：可继承。**
  - 师门可继承。
  - 不可再授权。
- **授权师门关系**：接口预留，阶段四上链。

#### 3.2.5 与 Epic 2 的消费关系

- `agent_stage_state`（Epic 2，SQLite 本地）：**老师能力画像的当前状态**（五阶段）。
- 思想指纹（B 板块，客户端）：**老师决策模式的数学表达（内容层）**。
- **两者独立演化，非因果**：
  - 思想指纹演化（B 板块，客户端）：内容层变化。
  - 能力画像演化（Epic 2，SQLite 本地）：状态层变化。
  - 两者可能同期演进，但思想指纹**不「导致」**能力画像变化。
- **B 板块只读不写 `agent_stage_state`**。

#### 3.2.6 存储位置

- 客户端本地。加密存储。
- 不上云。
- 不上链（阶段二）。接口预留。

#### 3.2.7 与白皮书的对应

§1.2、§3.7、§5.4.1、§5.4.3。

### 3.3 子项 3：监护模式

#### 3.3.1 是什么

被照护者（不能自理者 / 未成年人）的数据独立存储、独立加密、独立归属。监护人持有代管私钥，代行数据主权。被照护者成年或恢复自理能力后，私钥归还。

#### 3.3.2 独立性

- 被照护者数据与监护人数据**独立存储、独立加密**。
- 监护人被除名，**不影响**被照护者数据。
- 被照护者的数据主权属于本人，监护人只是代管。

#### 3.3.3 独立身份公钥生成时机

- **入社区时生成**（不是出生时）。
- 系统为被照护者生成独立 Ed25519 身份密钥对。
- 与监护人密钥一起管理。
- 该密钥对在成年之前由监护人**代为保管**，但**不得用于代签**被照护者的确认。

#### 3.3.4 成年触发

- 出生日期自动触发 + 双签。
- **双签构成**：
  - 被照护者用**独立身份私钥**签名确认。
  - 监护人用**代管私钥**签名确认。
- **防伪约束**：被照护者的签名必须由独立身份私钥生成，不能是监护人代点。
- **双签齐备**才完成数据主权归还。

#### 3.3.5 恢复自理能力的判定流程

「恢复自理能力」与「成年」是两条独立的归还路径。成年有出生日期自动触发；恢复自理能力需要定义判定流程。

**判定流程**：

1. **监护人主动放弃代管**：监护人提交放弃代管声明。
2. **社区一位老师确认**：由**被照护者（或监护人）当前任一 active 老师**，通过 C 板块状态判断接口（`judgment_type = SELF_CARE_ABILITY`）确认被照护者已具备自理能力。
   - 状态判断写入 C 板块 `state_judgment` 表（C 板块 v0.5 §6.6）。
   - 同时写入 `agent_stage_log`（`event_type=STATE_JUDGMENT`）。
   - B 板块不定义 `state_judgment` 表结构，只消费。
3. **双条件齐备**：监护人放弃 + 老师确认（`judgment_result = TRUE`），才触发数据主权归还。

**「当前任一 active 老师」的优先级**：

- 若被照护者本身已有独立师门归属（即 `patient_teachers` 表中有该被照护者的记录），则由**被照护者当前任一 active 老师**确认。
- 若被照护者尚无独立师门归属（`patient_teachers` 表中无记录，归属为 `''`），则由**监护人当前任一 active 老师**确认。
- 两者取其一，不叠加。

**为什么需要老师确认**：

- 防止监护人单方逃避责任（如不愿继续承担照护义务）。
- 老师确认是社区层面对「被照护者是否真的能自理」的专业判断。
- 被照护者未成年或无法自证时，老师确认是必要的第三方背书。
- 老师的专业判断与背书责任，构成对监护人单方操作的制衡。

**归还后**：

- 代管私钥失效。
- 独立身份私钥正式由本人持有。
- 数据主权自动归还。

#### 3.3.6 代际隔离

- 父母过错不及子女。
- 监护人被除名，不影响被照护者数据。
- 被照护者的信誉独立。

#### 3.3.7 智能体实现

- 不新增独立智能体。
- 学生智能体增加「监护模式」，同时管理学生自己的档案和被照护者的档案。
- 所有被照护者的数据操作，必须经监护人确认。

#### 3.3.8 存储位置

- 客户端本地。加密存储。
- 独立于监护人数据存储。

#### 3.3.9 与白皮书的对应

§1.6、§2.6.6、§2.7.2、§5.4.4。

### 3.4 子项 4：数据导出 / 迁移

#### 3.4.1 是什么

学生可随时导出自己的完整档案。老师可随时导出自己的思想指纹与师门模板。迁移格式开放，不锁定。迁移不需要平台批准。

#### 3.4.2 导出范围

| 角色 | 导出范围 |
| :---- | :---- |
| 学生 | 完整档案（姓名、家庭关系、症状、舌象、语音、病历、处方、段位记录） |
| 老师 | 思想指纹、师门模板、师承链（仅自己名下部分） |
| 被照护者 | 由监护人代管导出 |

**不包含**：

- 本地 SQLite 表的信任数据（`agent_stage_log`、`agent_stage_state`、lineage 表、`state_judgment` 表）。
- 链上信任数据（E 板块预留）。
- 其他学生的数据。
- 其他老师的思想指纹。

#### 3.4.3 导出格式

- **主格式**：JSON。
- **可选格式**：CSV（仅用于表格化数据，如指标趋势、病历列表）。
- **不做自定义二进制格式**。

#### 3.4.4 同步友好性预留

- 阶段二不做多设备同步。
- 但加密 blob 格式需预留同步友好性：自描述、可分片、可版本化。
- **加密 blob 结构**：

```json
{
  "version": "1",
  "field_id_hash": "sha256(field_id)",
  "key_id": "field-key-name-v1",
  "nonce": "...",
  "ciphertext": "...",
  "tag": "..."
}
```

- **自描述**：不依赖客户端本地状态即可解读。
- **可分片**：每个字段独立 blob，可单独同步。
- **可版本化**：`version` 字段支持未来演进。
- **tombstone 兼容**：blob 的 `version` 与字段私钥包的 `last_blob_version` 对齐，确保同步/迁移时旧 blob 不可回放。

#### 3.4.5 迁移语义

- 导出后可导入其他客户端，数据一致性由格式保证。
- **迁移口径：沿用 TD-003**（全库统一：只回收结构、不删业务列）。
- **B 板块不定义迁移口径**。

#### 3.4.6 平台角色

- 平台可提供导出工具，但**不代为保管**，**不承担数据丢失责任**。
- 导出不需要平台批准，不依赖平台服务器。

#### 3.4.7 与白皮书的对应

§5.4、§6.4.4、§6.4.5。

### 3.5 子项 5：数据封存

#### 3.5.1 是什么

数据封存 = 客户端下线。下线 = 不再对外服务，不再参与社区交互。数据不删除、不篡改、不审查。数据仍在客户端本地，只有当事人自己能访问。

#### 3.5.2 封存语义

- 封存的是**客户端**，不是数据。
- 数据从未离开客户端。

#### 3.5.3 触发条件

封存是**动作**，除名是**原因**，两者独立。

| 触发路径 | 原因 | 动作 |
| :---- | :---- | :---- |
| 老师被社区除名 | 除名 | 智能体封存 |
| 学生被所有老师除名 | 社区除名 | 客户端封存 |
| 老师不活跃下线 | 不活跃 | 客户端下线 |

#### 3.5.4 「学生被所有老师除名」的判定口径

**判定口径**：

「所有老师」= 该学生在 `patient_teachers` 表（概念名：`student_lineage`，Epic 4 交付）中**当前 active 状态**的全部老师。

**判定流程**：

1. 查询 `patient_teachers` 表，找出该学生当前所有 active 状态的老师。
2. 逐一检查每位老师是否已将该学生除名（记录在 `agent_stage_log`）。
3. 若**全部 active 老师均已除名**，则触发社区除名。
4. 若尚有任一 active 老师未除名，则不触发。

**对齐 Epic 4 表结构**：

- `patient_teachers` 是 Epic 4 交付的 SQLite 本地表，概念名 `student_lineage`。
- Epic 4 §2.2 决策：概念名 `student_lineage`，实现名 `patient_teachers`。
- B 板块以此对齐，**不新建表**。
- 若 Epic 4 表结构有变更，B 板块对齐变更，不另建状态。

#### 3.5.5 数据源

## 5. 技术选型

### 5.1 加密算法

| 用途 | 算法 | 理由 |
| :---- | :---- | :---- |
| 对称加密 | AES-256-GCM | 认证加密，防篡改；硬件加速普及 |
| 助记词编码 | BIP-39（12 或 24 词） | 工业标准；用户友好；跨钱包兼容 |
| 熵拉伸 | Argon2id | 内存硬，抗 GPU/ASIC |
| 种子→扩展私钥树 | BIP-32 | 分层确定性密钥树 |
| 扩展私钥树→子密钥 | HKDF-SHA256 | RFC 5869 标准 |
| 签名 | Ed25519 | 高性能；短签名；广泛支持 |
| 哈希 | SHA-256 | 字段 ID 哈希、tombstone 签名 |
| 随机数 | CSPRNG（系统级） | 所有 nonce、私钥生成 |

### 5.2 密钥派生链（完整版）

```
助记词（BIP-39）
  └─ Argon2id ─→ 种子（64 字节）
       └─ BIP-32 ─→ 扩展私钥树（xprv）
            └─ 根密钥（即主密钥，Master Key）
                 ├─ HKDF-SHA256 ─→ 主数据密钥
                 │                    └─ AES-256-GCM ─→ 加密「随主密钥」字段
                 └─ AES-256-GCM ─→ 字段私钥包（含 tombstone）
```

**说明**：

- BIP-39 是助记词编码，不直接派生密钥。
- Argon2id 做熵拉伸。
- BIP-32 派生**扩展私钥树**，根节点是主密钥。
- 保留 BIP-32 的目的：为将来按师门派生独立子密钥预留空间。
- 主密钥是密钥层次的根，助记词恢复的是主密钥。

### 5.3 加密 blob 结构

```json
{
  "version": "1",
  "field_id_hash": "sha256(field_id)",
  "key_id": "field-key-name-v1",
  "nonce": "...",
  "ciphertext": "...",
  "tag": "..."
}
```

### 5.4 字段私钥包结构

```json
{
  "field_id_hash": "sha256(field_id)",
  "key_id": "field-key-name-v1",
  "status": "active" | "deleted",
  "last_blob_version": 3,
  "encrypted_key_material": "...",
  "deleted_at": null | "2026-10-01T...",
  "tombstone_signature": "..."
}
```

**关键设计**：

- `field_id_hash` 用哈希，不泄漏删除的字段名。
- 删除 = tombstone 标记，不物理移除。
- `last_blob_version` 防重放。
- `tombstone_signature` 用主密钥签名，防篡改。
